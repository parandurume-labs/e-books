CHAPTER 14

Scheduling: it runs even when people forget

One scheduled task outlives any weekly-review habit

about 18 min

Let's take stock of what you have built. You have a vault (Part 2), an ontology (Part 3), and rules, templates, and skills (Part 4). Quite a lot of work gets done now, as long as a person asks for it.

Here is the problem. Nobody asks.

Chapter 1 put down "20 minutes of weekly review." Those 20 minutes hold through the first month, slip to every other week in the second, and vanish in the third. You are busy. When the review goes, rule violations pile up. When violations pile up, the quality of AI answers drops. When quality drops, nobody uses the thing.

What this chapter is for

The biggest reason a knowledge system dies three months in is that work that depends on remembering to do it is still sitting there. This chapter takes that work off human memory and bolts it to the clock.

In the layer model from Chapter 3, what you build here is half of layer 3.

Your default tool is a Cowork scheduled task

Claude Cowork has scheduled tasks. Write the prompt once and it runs on a set rhythm and leaves its output behind. The feature arrived in February 2026, and it needs a paid plan (Pro, Max, Team, or Enterprise).

  1. Click "Scheduled" in the left sidebar

    The list of scheduled tasks opens. The first time, it is empty.

  2. Click "New task" and pick how to set it up

    Create with Claude lets you describe what you want in plain words, and Claude proposes a prompt and a frequency. Set up manually means you type it in yourself. For the first two or three, building them by hand teaches you the structure.

  3. Fill in the manual fields

    Task name, prompt, approval mode, frequency, and then optionally a model and a folder.

  4. Pick a frequency

    Hourly, daily, weekly, weekdays, or manual. There is nothing as fine-grained as "the last business day of the month." If you need that, set it weekly and let the prompt work out the date.

  5. Save, and you are done

    From then on you read the run history and the output from the list.

How specs are dated here

The screens and frequency options in this chapter are as of July 2026. This feature still moves fast, so if a button has a different name, look for "Schedule" or "Scheduled." What matters in this chapter is not where a button sits but the constraint in the next section. That one is not changing any time soon.

Remote runs and a local vault: this is where most people get stuck

The best thing about a scheduled task is that it runs remotely. Close the laptop, quit the Claude app, and it still runs at the set time.

That is exactly what causes the trouble.

The constraint that matters, so read this one twice

A scheduled task running remotely cannot reach a local folder on your PC. It only handles connectors and files stored in your Claude account.

Your vault, though, is a local folder like C:\Users\...\OneDrive - Company\Solbit Tech Wiki\. Chapter 4 called working on that folder directly the advantage of this combination. In a scheduled task, the same thing turns into the limit.

There is one exception. If a task needs local files, that task runs only locally. Which means the computer has to be awake at that hour with Claude Desktop open. If it is off, that run is simply skipped.

Set up "check the vault every Monday morning and write me a report" without knowing this, and nothing happens until you get to the office on Monday and turn the machine on. The worse case is a run that goes ahead, cannot read the vault, and hands you an empty report. Somebody really did trust a report that said "checked, no problems found" for three weeks.

So you use four paths

No single one covers everything. Each is good at something different.

Runs whereVault accessPC can be offAI judgmentMainly used for
A. Local scheduled task Cowork (local) reads and writes directly ❌ must stay on yes work that has to change the vault (structuring, checks, retrospectives)
B. Remote scheduled task Cowork (cloud) through a connector (SharePoint, OneDrive) ✅ yes work that reads and tells you (briefings, summaries, watching)
C. Task Scheduler Windows + Python reads and writes directly ❌ must stay on none (rules only) work with the same result every time (format checks, dashboard generation)
D. Power Automate Microsoft 365 cloud reads through SharePoint ✅ none work that pushes out to Teams (digests, reminders)

You get the answer by asking the questions below in order.

The first three scheduled tasks to build

Do not build more than five. To start with, three is about right. The three below are a deliberate set, in this order. One helps you start the week, one nudges people to record, one protects quality.

① Monday morning briefing (Path B · remote)

Monday, 08:30. Before you get in, it lays out what you need to look at this week. It only reads, so run it remotely.

[Task name] Monday weekly briefing
[Frequency] Every Monday 08:30 (KST)
[Approval mode] Automatic
[Prompt]

Using the "Solbit Tech Wiki" folder on SharePoint, write this week's briefing.

Include:
1. Items due within 14 days — based on the due field in Sources/20-Projects/.
   List projects and opportunities separately, and give the owner alongside each.
2. Notes created or changed in the last 7 days (based on the updated field).
3. Decisions recorded in the last 7 days — find them in Sources/40-Worklog/.
4. Products with status 운영 that have had no update for 14 days or more — a stale signal.

Rules:
- Never infer a fact that is not in the vault. If it is missing, write "no record".
- After each item, put the name of the source note in [[double brackets]].
- Under 1000 characters. No tables, short lists only.
- If every section is empty, write the single line "nothing unusual this week".

② Daily 6 pm work log check (Path B · remote)

The retrospective in Chapter 18 only works if the work logs exist. And nobody writes work logs. So you tell only the people who skipped, quietly.

[Task name] Missing work log check
[Frequency] Weekdays 18:00 (KST)
[Approval mode] Automatic
[Prompt]

In Sources/40-Worklog/, find the work log notes written with today's date (KST).

- Take the team roster from Sources/00-Company/members.md.
- List only the names with no log for today.
- If everyone has written one, output the single line "all logs in" and stop.
- Do not write a sentence that blames anyone. Names and numbers only.
- Count yesterday and the day before too, and mark it like "2 days missing in a row".

This task is not a surveillance tool

Post the list of missing logs to the whole team channel and this system dies that day. People read recording as monitoring, and then you get logs that fill the form and say nothing. Logs like that are no use in a retrospective.

Send it to the person alone, or let one knowledge owner see it. Once everyone has logged for three weeks straight, delete the task. Once the habit is there, the alert is noise.

③ Friday evening quality check (Path A · local)

This one has to change the vault, so run it locally. Set it for Friday at 17:00, an hour when people are still at their desks.

[Task name] Weekly vault check
[Frequency] Every Friday 17:00 (KST)
[Approval mode] Confirm before writing files
[Folder] Solbit Tech Wiki
[Prompt]

1. Run _ops/scripts/validate.py.
2. Sort the results into ERROR / WARN / INFO.
3. Fix these kinds of ERROR yourself.
   - a missing required updated field → fill it with the file's modification time
   - a typo in a class value → check it against the list in _ops/01-ontology-design.md and fix it
4. Leave the rest alone and only list it. In particular, do not touch anything that needs a judgment about the facts.
5. Save the result as _reports/check-YYYY-MM-DD.md. Do not overwrite an existing file.
6. Compare with last week's report (the newest file in _reports/) and put the change in ERROR count on the first line.

Never do this:
- do not edit the body of a note under Sources/ (anything below the frontmatter)
- do not change any field on a note with confidence: reviewed
- do not create new notes

Put those three in place and a week looks like this.

A scheduled prompt is not a chat prompt

For the same job, the prompt for a scheduled task runs longer. There is a reason. In a chat you say "no, not that" when the output looks off; in a scheduled task nobody is there to say it.

So you always write six things.

RuleSkip it andWrite it like this
1. Exactly where the output goes the result stays in the chat window and disappears save as _reports/check-YYYY-MM-DD.md
2. What to do when the result is empty you collect weekly reports that say "nothing to report" at length if empty, write one line and stop
3. A list of things never to do it quietly edits a note a person had verified do not touch reviewed notes
4. Sourcing is mandatory you cannot tell where a number came from, so you check it again anyway source note after each item in [[brackets]]
5. Comparison with the last run you cannot tell whether things are getting better or worse compare with the last report, change on line one
6. A length cap nobody reads it three weeks later under 1000 characters

Number 2 matters most

Automation dies of noise, not of stopping. If a report arrives daily and daily says nothing much, people stop reading it within three weeks. They miss the run that mattered along with the rest.

Build it so that silence is the answer when nothing changed. The arrival of the alert should itself be information.

How to pick the approval mode

Kind of taskApproval modeWhy
Reads and summarizes only (briefings, alerts)automaticNothing to undo. Ask for confirmation and the run just sits there
Creates new files only in a generated-output folderautomaticIt does not touch existing knowledge
Edits notes in Sources/needs confirmationIt changes knowledge a person verified
Deletes or moves filesneeds confirmation (or ban it outright)Sync conflicts and broken links arrive together

The trap of stalling quietly on approval

A task set to "needs confirmation" that fires at 3 a.m. sits there waiting for approval. Nothing happens until you look in the morning. And when the next run comes around, you have forgotten that the last one is still stalled.

Two ways out. Schedule tasks that need approval for hours when a person is at the screen (Friday at 17:00, say), or limit their writing to _reports/ and run them automatically. This book recommends the second.

Path C: Python plus Windows Task Scheduler

Plenty of work needs no AI at all. "Is the required field there," "is this link broken," "how many notes are there" is arithmetic, not judgment. A script does that better. The result is the same every time, it costs nothing, and it spends no AI usage.

Here is how to run the validate.py you build in Chapter 17 automatically every morning. One line in an administrator command prompt.

schtasks /create /tn "Wiki check" /tr "python \"C:\Users\hong\OneDrive - Solbit Tech\Solbit Tech Wiki\_ops\scripts\validate.py\"" /sc daily /st 08:00 /f

The options look unfamiliar, but four of them are enough.

OptionWhat it means
/tnTask name. You use it later to delete the task (schtasks /delete /tn "Wiki check")
/trThe command to run. If the path has spaces, escape the inner quotes as \"
/scFrequency. daily / weekly / hourly / onlogon
/stRun time (24-hour clock)

onlogon may serve you better than 08:00

Set it for 08:00 and any day the PC is off at that moment gets skipped. With /sc onlogon it runs every time you log in, so it runs once a day even when your start time moves around.

Put "exit if it already ran today" in the first line of the script and several logins still give you one run.

Have the script leave a report and nobody has to read it. A Cowork scheduled task reads that report and puts it into human words. C calculates, A and B interpret — that split holds up best.

# the last part of _ops/scripts/validate.py
# leave it for the next automation, not for a human

report = ROOT / "_reports" / f"validate-{today}.md"
report.write_text(rendered, encoding="utf-8")

# append one summary line so the scheduled task can work out the change
with (ROOT / "_reports" / "validate-history.csv").open("a", encoding="utf-8") as f:
    f.write(f"{today},{n_error},{n_warn},{n_notes}\n")

Those last two lines are the raw material for the trend chart in Chapter 15.

Path D: pushing to Teams with Power Automate

Even a report you generate might as well not exist if nobody opens that folder. So you push the result up into a Teams channel.

If you use Microsoft 365, Power Automate is already there. The flow has four steps.

  1. Pick a trigger

    Use Recurrence, every Monday at 09:00, with the time zone set to Seoul. Leave the time zone alone and it runs on UTC, nine hours out.

  2. Read the file

    SharePoint - Get file content pulls the newest report from _reports/. The vault lives in a Teams shared folder, so SharePoint sees it as it is.

  3. Pull out only the part you need

    The first ten lines of the report are plenty. Put the whole thing in a card and nobody reads it. Attach a link for "see details."

  4. Post it to Teams as a card

    Use the Post your own adaptive card as the Flow bot to a channel action. Aim it at the knowledge channel.

For the card body (Adaptive Card JSON), this much is enough.

{
  "type": "AdaptiveCard",
  "version": "1.4",
  "body": [
    { "type": "TextBlock", "text": "Weekly wiki check", "weight": "Bolder", "size": "Medium" },
    { "type": "TextBlock", "text": "@{outputs('summary')}", "wrap": true },
    { "type": "FactSet", "facts": [
      { "title": "ERROR", "value": "@{variables('nError')}" },
      { "title": "vs last week", "value": "@{variables('delta')}" },
      { "title": "Total notes", "value": "@{variables('nNotes')}" }
    ]}
  ],
  "actions": [
    { "type": "Action.OpenUrl", "title": "Open the report", "url": "@{variables('reportUrl')}" }
  ]
}

How many alerts can you build

Technically, no limit. Organizationally, three a week is the ceiling. Past that, people mute the channel. And once they mute it, they miss the announcements that really matter.

Every time you add an alert, look at an existing one as a candidate for deletion. That single rule doubles the life of an automation project.

Three new problems automation creates

1. Sync conflicts go up

The OneDrive conflict problem from Chapter 6 comes back here. When a scheduled task touches the same file as a person, you get a conflict copy. Scheduled tasks run overnight too, so you arrive one morning and there is a filename 1.md with no explanation.

One rule handles most of it

Automation writes new files only in generated-output folders such as _reports/ and _moc/. Sources/ belongs to people.

If an automation has to edit notes, have it leave a "to fix" list as a report and let a person approve and apply it instead of editing. It costs one more step, and it beats quietly contaminating your knowledge assets.

2. What AI wrote and what a person checked get mixed together

If a scheduled task creates notes every week, a few months later half the vault is AI output nobody has read. And the next AI reads it as fact. Repeat that and quality collapses quietly.

So automations always use the confidence field from Chapter 12.

confidence: draft      # AI made it, nobody has looked
confidence: reviewed   # a person read it and confirmed it
generated_by: schedule/weekly-briefing   # which automation made it

Put one line in CLAUDE.md as well. "A note with confidence: draft is never a source for an external document." That one line closes the route by which unverified information gets into a proposal.

3. Failure is quiet

This is the dangerous one. When a scheduled task stops running, nobody knows. Nobody registers the fact that no alert arrived. Some weeks have no alerts anyway.

So you make sure one of them arrives every week without fail. That is why the Monday briefing is designed to send "nothing unusual this week" as a single line. One line arriving means the system is alive. Two weeks of silence is a signal that something broke.

Solbit Tech in practice: deleting two of five scheduled tasks

Solbit Tech ran five scheduled tasks for three months. Here is how it came out.

TaskThree months later
Monday weekly briefingKept. Kim uses it as the material for the Monday meeting
Weekly vault checkKept. ERRORs fell from 19 to 3, then stayed there
Missing work log checkDropped. By week seven everyone was logging, so the alert had become noise
Daily news summaryDropped. General information unrelated to the vault, and nobody read it
Month-end numbersKept, but moved. Letting AI count made them uneasy, so it went to Python (C)

The part worth noticing is that dropping something is not a failure. The missing-log alert stopped being needed because it succeeded at building the habit. An automation that met its purpose should go.

The daily news summary, on the other hand, was the wrong automation from the start. It neither read the vault nor wrote to it. It got built because it was easy to build, and that kind rarely gets used.

Once a quarter, clean up your automations

Scheduled tasks only ever multiply. So every quarter you open the list and ask three things of each one.

Three questions for a cleanup

  • Has anyone actually opened any of its output in the last four weeks? If not, delete it. "We might need it someday" means you do not need it.
  • Has anything it produced been quoted in another document? Then it stays. That is evidence it is in use.
  • Has it met its purpose, so it is no longer needed? An alert meant to build a habit goes once the habit is there.

Try it: build one scheduled task

Do not build all three. Building one and running it for two weeks goes much better.

  1. Use the decision tree above to pick the path for the task you build. For your first one, take B (remote, read only). If it fails, the vault survives.
  2. Copy the "① Monday morning briefing" prompt and swap in your own folder names and field names. Used as it is, it will not run.
  3. Before you set the frequency, run it manually once. If the output looks off, fix the prompt. Two or three rounds of that is normal.
  4. Find one wrong fact in the output. When you find it, it is a vault problem, not a prompt problem. Work out which note was empty and caused it.
  5. Two weeks later, ask yourself: "Did I actually read this alert?" If not, delete it and build something else.

Quick recap

  • A knowledge system dies because of the work that depends on remembering. Bolting that work to the clock is what this chapter is for
  • A Cowork scheduled task runs remotely but cannot reach a local folder. A task that needs local files runs only while the PC is awake
  • Split the work across four paths. A local task (writes) · B remote task (reads) · C Python plus Task Scheduler (calculates) · D Power Automate (tells people)
  • The order you ask in: does it need AI judgment → does it write to the vault → can the PC stay on
  • A scheduled prompt always says six things. Where the output goes, what to do when the result is empty, what never to do, sourcing, comparison with the last run, and a length cap
  • Automation dies of noise, not of stopping. Build it to say nothing when nothing changed
  • Automation writes only to generated-output folders (_reports/, _moc/). Sources/ belongs to people
  • Leave confidence: draft and generated_by on AI output. It stops the unverified from leaking into external documents
  • Failure is quiet. Make one task arrive every week and use it as a sign of life
  • An automation that met its purpose gets deleted. Dropping it is not a failure

Coming up

Once the automation runs, reports pile up. And a report made of prose stops being read in week three. So you make it visible instead. Status field design, Gantt charts drawn with no plugins, kanban boards, and a dashboard note that refreshes itself every week. The moment the benefit of recording becomes visible, people start recording.
