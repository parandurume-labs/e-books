CHAPTER 13

Automating repeat work with skills

The third time you explain the same thing, write it down

about 22 min

Structuring meeting notes took six weeks to settle in at Solbit Tech. In week six this happened.

The decision note Park made had no link back to the source. The source: box was empty. The note Lee made had Daesung Logistics written out by name, when it should have carried confidential: 대외비 as a pre-contract customer. Kim's note got both of those right but had no "options considered and not taken" box.

All three were being diligent. All three were simply using different prompts. One person wrote the first prompt, everyone copied it, everyone tweaked it a little, and over six weeks it split three ways.

What this chapter is for

A prompt is speech. Speech shifts a little every time it passes through a person. A skill is that speech frozen into one file and called by name.

In the layers from Chapter 3, a skill is layer 3 machinery. Not one line of company fact goes in. Only procedure. That distinction runs through the whole chapter.

A skill is a work manual

Say someone new joins. Explain "how we tidy up meeting notes" out loud each time and by the third go you leave something out. So you write it down once and say "follow this." That document is a work manual.

A skill is a work manual you give to AI. Instead of explaining every time, you write it once and call it by name. Say "handle this with the meeting note skill" and it moves through the steps in that file.

Chapter 11 separated rules (CLAUDE.md), formats (templates) and procedures (skills). The dividing question was "does this rule bind every task, or only one task?" That table does not need reopening. Two things get added on the skill side.

First, a skill is only read when called. CLAUDE.md goes into every conversation, while a skill opens when its name comes up. So writing it long does not weigh down ordinary conversations. Twenty lines of meeting-note procedure make no difference at all to a conversation about writing a proposal.

Second, make a skill only when there are two or more steps. Something with an order to it, like "save the source, extract, report as a table, create after approval." A one-step job is not worth a skill. Write it into _ops/prompts.md as a prompt and copy it when you need it.

When to freeze something into a skill

One test. You have used the same prompt three times, and it barely changed across those three. Chapter 16 applies the same test again across twelve recipes.

If you are still editing it, do not make it a skill. Editing a skill is more of a chore than editing a prompt. A skill preserves a settled procedure. It does not invent one.

What a SKILL.md looks like

As of July 2026 the minimum is one folder holding one SKILL.md. The folder name becomes the skill name.

Solbit Tech Wiki/ ├── .claude/ │ └── skills/ │ ├── wiki-ingest/ │ │ └── SKILL.md pull notes out of source material │ ├── wiki-retro/ │ │ └── SKILL.md retrospective │ └── wiki-audit/ │ └── SKILL.md check for rule violations ├── _ops/ └── Sources/

The top of the file carries frontmatter, and below that it is an ordinary markdown document. The frontmatter needs two things.

---
name: wiki-ingest
description: Pull decisions and actions out of meeting notes, transcripts and outside
  documents, and turn them into vault notes. Use when tidying up a meeting note or
  structuring material you received.
---

The description is the most important part of this file

The body is read after the skill is called. The description is what decides whether to call it. Weak here, and however well you wrote the body, it never runs.

So write both things. What it does and when to use it. Stop at "handles meeting notes" and it does not fire when someone says "tidy up this transcript file for me." Put the words a user would actually say into the description.

The body runs to six sections. Those six are the standard skeleton this book uses.

SectionWhat goes in itLeave it out and
When to usetwo or three situations that call this skillit fires in the wrong situations
Inputwhat it needs before it can startit starts with no material and invents some
Procedurenumbered stepsthe order changes every time
Ruleswhat to hold to at each stepthe field conventions from Chapter 12 collapse
Outputwhere it lands and under what nameit stays in the chat window and vanishes

That last section is the longest. There are four mistakes AI makes while trying to help. It filled in background, it corrected an out-of-date value, it completed a name, and it smoothed the wording. Every one was an attempt to help and every one was an accident. A skill that handles company facts becomes a list of "do not," rather than "do it well." How those four show up in a real prompt, and the one line that stopped each, you see directly in ⓕ of recipe 1 in Chapter 16.

Three skills are enough

Start with three. They attach at three different points in the vault's life.

SkillWhat it doesWhen you call itChapter 16 recipe
wiki-ingestpulls decisions, actions and fact changes out of a sourceright after a meeting (manual)input for 1 and 5
wiki-retrocompares intent against executionlast week of the quarter11
wiki-auditfinds notes that break the ontology conventionsonce a month9

The right-hand column maps onto the working recipes in Chapter 16. Recipes 1, 9 and 11, the ones Chapter 16 picks out as worth freezing into skills, pair one-to-one with these three. The weekly report (recipe 3) stays a prompt rather than a skill, because a week is too short a window to produce a difference worth comparing, so there is no procedure to freeze. The terminology audit (recipe 10) is not a skill either. Chapter 16 nails it down as Python's job because it is string matching and needs no AI. The rest are either one-off events (job adverts, onboarding packs) or prompts that still change too often to freeze.

The order of building is fixed too. Build wiki-ingest first and the other two a month later. The reason is simple. wiki-retro only runs once work logs have piled up, and wiki-audit only runs once there are notes to check. Hang a retrospective skill on an empty vault and you get three lines of "no record." It is the same species of disappointment as Solbit Tech breaking the order in Chapter 16.

wiki-ingest

The one you use most and the one that matters most. Build only this and you are half done.

---
name: wiki-ingest
description: Pull decisions and actions out of meeting notes, transcripts and outside
  documents, and turn them into vault notes. Use when tidying up a meeting note or
  structuring material you received.
---

# Structuring source material

## When to use
- After a meeting, putting the memo into the vault
- Putting a document or a public call received from outside into the vault

## Input
- One piece of source text, or one file path
- Without it, do not start. Ask for the source

## Procedure
1. Save the source first.
   Meeting memos go in Sources/40-Worklog/, material received from outside and
   transcripts go in Sources/90-Reference/.
   Name the file YYYY-MM-DD-title.
2. Pull four things out of the source.
   - Decisions: anything of the form "we decided to". With the alternatives and the reasoning
   - Actions: anything with an owner and a date
   - Fact changes: anything that changes a field on an existing note
   - New entities: organizations, products or technologies with no note yet
3. Report what you pulled out as a table. Do not create files yet.
4. Create or edit notes only after approval.
5. Use the matching template from _ops/templates/ for any note you create.
6. Finally, add links to the "Extracted from this" section of the source note.

## Rules
- New notes are created with confidence: draft
- Every extract links back to the source with source:
- Never fix content that contradicts an existing note. Report it separately as a contradiction
- Mark pre-contract customers as confidential: 대외비
- Never smooth over something ambiguous. Leave it as 확인 필요

## Output
- 1 source note (never modified)
- 0 or more extracted notes
- A report table (in the chat window)

## Do not
- Never edit the source. Leave the typos and the broken sentences
- Never infer a fact that is not in the source
- Use people's names exactly as written in the source. Never guess a title and attach it
- Never set confidence to reviewed. Only people change that
- Never create or edit files under Sources/ without approval

Steps 1 and 3 are the backbone of this skill. Seal the source first, and report as a table first. Take those two out and eight notes appear at once, two of them wrong, with no easy way to tell which.

wiki-retro

The retrospective skill. The reasoning behind the design is in Chapter 18. Here you only freeze the procedure.

---
name: wiki-retro
description: Compare work logs against project notes and lay out the gap between plan
  and actual. Use for a quarterly retrospective, or when someone asks
  "what did we actually do this quarter?".
---

# Intent against execution retrospective

## When to use
- The quarterly retrospective in the last week of the quarter
- Revising the quarterly plan mid-way

## Input
- A period (start date and end date). Without one, use the previous quarter

## Procedure
1. Gather the work logs for that period from Sources/40-Worklog/.
2. Follow each log's pdm_intent_of link and open the target project or opportunity note.
3. Group by project and lay each one out in three lines.
   - Plan: that project note's stage and due
   - Actual: what the logs actually record
   - Gap: where the two diverge
4. Collect logs with no pdm_intent_of separately as "work not connected to anything".
5. Mark days with no log as "no record". Never fill them in by guessing.

## Rules
- Write around "progress and blockers", not "what I did"
- On finding a gap, do not assert a cause. Record the gap only
- Never write a sentence that evaluates a person. Names and facts only
- Under 1500 characters

## Output
- _reports/retro-YYYY-QQ.md
- On the first line, the change in "work not connected to anything" against last time

## Do not
- Never edit notes under Sources/
- If the logs are empty, do not produce a retrospective. Leave one line saying "no record"
- Never add unplanned work into the plan after the fact

"Never write a sentence that evaluates a person" is this skill's survival condition

Let one sentence like "Park is behind schedule" appear in a retrospective report and, from the following week, the work logs get written well. Written to look good. And a log written to look good is useless for a retrospective.

It is the same reason as "do not post the missing-log alert to the team channel" in Chapter 14. The moment a record feeds into evaluation, the quality of the record collapses.

Do not let them overlap. Hand a skill something a script could catch and you pay money for a less accurate answer. The same test that divided path C from path A in Chapter 14 applies here unchanged.

---
name: wiki-audit
description: Find where vault notes have drifted from the ontology design document and
  leave a report. Use for the monthly check, or when someone asks
  "how is our vault doing?".
---

# Vault convention check

## When to use
- The first Monday of every month
- Right after editing the ontology design document

## Input
- _ops/01-ontology-design.md and _ops/02-terminology.md
- Without them, do not start

## Procedure
1. Read the latest results from _ops/scripts/validate.py first.
   Do not look again at anything it already caught.
2. Look only at the four things the script cannot catch.
   - a number written down with no link to an evidence note
   - confidence: reviewed with an empty evidence section
   - frontmatter values that disagree with the body text
   - different values recorded for the same entity
3. Report only what is certain. If it is borderline, do not report it.
4. Maximum 3 items. Beyond that, keep the 3 most serious.
5. For each item, name the file and the line number.

## Rules
- Fix nothing. Produce a list only
- Compare with the previous report and put the change on the first line
- If there are no violations at all, write one line: "no violations"

## Output
- _reports/audit-YYYY-MM-DD.md

## Do not
- Never edit or create files under Sources/
- Never repeat an item the script has already reported
- Never write "suggested improvements". Facts only

Without the two files in the Input section, this skill does not start. That is deliberate. With nothing to compare against, a check is just impressionistic criticism. You built the design document in Part 3, but you have never built the terminology list. A minimal two-column format is in Appendix B, so copy it from there and save it as _ops/02-terminology.md. Three lines is a fine start.

"Maximum 3 items" matters. Recipe 9 in Chapter 16 uses the same cap. Nobody fixes a twenty-three item report. Three items you can fix in an hour, and next month three more arrive. Done this way, violations go down. Receive twenty-three in one go and the skill is switched off that day.

Two ways to get skills to the team

Use a skill on your own and half this chapter is pointless. The problem at the top was three people using three different procedures. There are two ways to distribute.

Shipped in the vaultShared org-wide
Where it lives.claude/skills/ inside the vaultdeployed from the org admin screen

New joinersarrives with the vaultnothing to do

Confidentialityfollows the vault permissionsthe whole organization sees it

The decisive difference is the versions row. Skills reference folder names and field names. Rename Sources/90-Reference/ to Sources/95-Archive/ and the skill has to change with it. Ship it in the vault and the two sit in one folder and move together. Keep them apart and one day they quietly drift.

The order to use

Ship in the vault for the first three months. In that period you edit skills often, and if every edit goes through an admin nobody edits them. A skill nobody edits becomes a skill nobody uses.

When a skill goes three months without an edit, that is your candidate for org-wide sharing. It means the procedure has settled. And when you do share it org-wide, remember that the skill body spells out your company's folder structure and field names. That is not information to send outside the organization.

Whether you can share skills at the organization level depends, as of July 2026, on your plan and admin settings. Check with your admin before you commit, and if it is unavailable, shipping in the vault is plenty.

For a company like Solbit Tech, five people on one vault, shipping in the vault finishes the job. Whoever edited the skill is sitting next to you, and when they say so, the whole team knows that day. Look at org-wide sharing when you have more than one vault, or when you want to give the same procedure to people who do not use the vault.

Sync delay makes ghost bugs

Shipping in the vault has one trap. Edit the skill file and it takes time to reach other people's machines. In between, two people calling the same skill get different results.

And it looks like a bug. "It worked yesterday but not today?" In fact there are two copies of the file.

The fix is simple. Tell the team in one line whenever you edit a skill. And put the date of the last edit at the bottom of the skill body. When a result looks wrong, start by checking that date.

The decision to take plugins out

Let me be straight. A good deal of what the three skills in this chapter do could be done with Obsidian community plugins. Automatic template insertion, automatic note creation, field aggregation, dashboard refresh. Good plugins exist for all of it.

But this book decided in Chapter 4 not to use plugins. Chapter 4 deferred "the reasoning for that call comes in Chapter 13," and this is the place. What it wrote down then were four things that actually happened.

  • The AI model the plugin used did not understand our company ontology.
  • It built notes in English out of Korean source material, so company proper nouns got translated and mangled.
  • It was structured to produce low-quality duplicate notes competing with human-verified ones.
  • Claude Cowork did the same job better.

All four read like circumstances of that one plugin. But follow each one back to why it happened and they gather into three reasons that come from the plugin approach itself. Pick a different plugin and you snag on the same three places. Here they are, and Chapter 15 checks them again.

1. There is no way to enforce installation across a team

Plugins are installed by each person into their own Obsidian. Share the vault and the plugins do not follow. So the goal of this chapter, "the whole team uses the same procedure," fails from the outset.

Every time someone joins you walk them through installation, and one of them will not do it. And only that one person's notes come out in a different format. In a five-person company that one person is 20% of everybody. The problem from the top of this chapter comes back with a different tool attached.

Chapter 4's third item, low-quality duplicate notes competing with verified ones, comes from here. Notes appear automatically only in the vault of whoever installed the plugin, and those notes sit outside the format the team agreed. The moment one entity has two notes, layer 2 splits.

2. Updates break it

Use a plugin and your vault is tied to someone else's release schedule. One day it updates, the syntax changes, and the dashboard goes blank. Nobody in the company can fix it.

It gets worse. The developer stops maintaining it. Now the lifespan of your company knowledge system depends on the circumstances of someone whose face you have never seen.

Chapter 4's first and fourth items snag here. We do not get to decide which model the plugin calls, nor whether there is any way to make that model read our ontology. That is why Cowork did the same job better. The difference is whether one instruction file can change the rules.

3. Knowledge gets locked inside the tool

This is the most important reason. Some plugins build a view out of a query syntax. Open a note written in that syntax without the plugin and you get a blank. The text is still there and it cannot be read.

Chapter 5 explained why we chose files over a database. Because the knowledge survives the tool. A note written in plugin syntax hands that advantage back.

Chapter 4's second item, company proper nouns mangled into English, is the light version of this. The format the tool chose ended up deciding the shape of our knowledge, and the moment Warebot is rewritten as WarehouseBot in a note, that note leaves our terminology list.

The test is one question

"If this tool disappears, does my knowledge disappear?"

If yes, do not use it. If no, go ahead. Chapter 15 confirms this again, but a plugin that only changes the view is relatively safe. Delete it and the notes are still there as markdown.

That test is why this book uses Mermaid. It is built into Obsidian, and being a markdown code block it stays readable as text in any other editor. The template feature in Chapter 12 sticks to core features for the same reason.

There is a price to pay. It takes more hands. Work a plugin would do with one button, you do with a prompt. A table that refreshed itself, you rebuild with a script.

Whether that price is worth paying differs by company. For a personal vault used by one person, a plugin is far more convenient. If the whole team uses one vault and it has to be readable in three years, this book's choice is better. The reasoning is written down, so decide differently if you like. What is worst is starting to install them one by one without deciding at all.

Three ways skills fail

1. Company facts get written into the skill

The most common one. Once you are using a skill you want to add lines like "the owner of an action is usually Park" or "link Warebot decisions to PRD-001".

It looks convenient and it is an accident. When Park leaves, the skill has to change, and nobody remembers that the name is in there. And a company fact written in two places will diverge.

The rule is one line. Facts in layer 2, procedures in layer 3. No people's names, product names or numbers in a skill. Folder paths and field names are fine. Those are structure, not facts.

2. You end up with too many skills

They are easy to make, so you get ten. Then two things happen. The description fields overlap so the wrong skill fires, and people cannot remember which skills exist.

Start with three. When you make a fourth, review one of the existing three as a candidate for deletion. Same reason as the alert rules coming in Chapter 14.

Before making a new skill, ask once more. "Could one extra line in an existing skill do this?" Usually it could.

3. Skills go quietly stale

The third trap from Chapter 12 gets one size bigger here. You add a box to a template and the skill still looks at the old list of boxes. No error appears. You find out two months later on the dashboard.

Now four files are one body. _ops/01-ontology-design.md · CLAUDE.md · _ops/templates/ · .claude/skills/. Change one and open the other three.

Remembering to compare those four every time is hard for a person. So Chapter 17 puts the comparison into the validation script. Anything you have to remember to do ends up not getting done.

Solbit Tech in practice: six weeks with three skills

Six weeks passed after the three-way prompt split at the top was merged into one wiki-ingest. The three skills met three different fates.

SkillSix weeks on
wiki-ingestKept. The morning after a meeting, three people now produce notes of the same shape
wiki-auditKept, after a fix. The first month's report had 23 items and nobody fixed any. It survived once "maximum 3 items" went in
wiki-retroKept, with a narrower scope. The weekly version said the same thing every week, so they dropped it and kept only the quarterly retrospective

The middle row is the one that matters. wiki-audit nearly died because it was diligent. It found every violation in the vault without exception and laid out twenty-three lines, and Kim opened the report twice and stopped opening it from the third time.

A check that finds everything fixes nothing. Only after the cap went on did violations actually start dropping by three a month.

And not making the weekly version a skill was not a failure either. A week is too short a window to produce a difference worth comparing, so it stayed as the weekly report in recipe 3 of Chapter 16. As Chapter 14 puts it, automation you will not need is not worth building in the first place.

Five questions that tell you whether a skill is any good

  • Is there a single line of company fact in it? Take it out. People's names, product names, numbers.
  • Is the "do not" section three lines or more? Two or fewer means you have not run the procedure enough yet.
  • Is the output file path written down? Without it, the result stays in the chat window.
  • Does it say what to do when the result is empty? Without that, you accumulate long-winded "nothing to report" files.
  • Can you tell when to call it from the description alone? Show it to someone else and ask.

Try it: build the ingest skill and run it twice

Do not build all three. wiki-ingest is enough. Thirty minutes.

  1. Let Cowork make the folder. Type this into the chat window. Create the folder .claude/skills/wiki-ingest/ at the top of the vault and save the following as SKILL.md. Paste the body above underneath, but change the folder paths and class names to match your vault. Used as is, it will not run.
  2. Run it once on last week's meeting note. Take it as far as the table and stop.
  3. Compare the table against the source. Any sentence you find that is not in the source is a line to add to "do not".
  4. Approve and let it create the notes. Then check that every source: link is in place.
  5. Run it again on a different meeting note. This is the important part. See whether the second result has the same shape as the first. If not, the procedure is not written out fully enough.
  6. Tell the team about the edited SKILL.md and have someone else run it on the same meeting note. When three people's results match, this chapter has done its job.

If you want to create the folder in File Explorer instead, you need one trick. Windows Explorer refuses folder names starting with a dot, but put a dot on the end too and type .claude. and it goes through. Once created it stays hidden from the Obsidian list, like .obsidian in Chapter 5. That is normal.

Quick recap

  • A skill is a work manual you give to AI. Write a repeated procedure into a file and call it by name
  • A skill is read only when called. So writing it long does not weigh down ordinary conversations. Build one only when there are two or more steps
  • Freeze it into a skill after using the same prompt three times. If you are still editing it, do not
  • SKILL.md is one file in one folder. The frontmatter needs name and description (as of July 2026)
  • The description decides whether it gets called. Write both what it does and when to use it
  • Six sections in the body: when to use · input · procedure · rules · output · do not. The last is the longest
  • Start with three skills: ingest (let it in) · retro (look back) · audit (find what drifted)
  • wiki-audit looks only at what you have to read to know. Anything countable belongs to the Python in Chapter 17
  • Two ways to distribute. Ship in the vault for the first three months. For five people on one vault that finishes it. Look at org-wide sharing when you have more than one vault
  • The trap in shipping with the vault is sync delay. Tell the team when you edit, and leave the edit date in the skill
  • Three reasons not to use community plugins: you cannot enforce installation · updates break them · knowledge gets locked in the tool
  • The test is one question: "if this tool disappears, does my knowledge disappear?"
  • Facts in layer 2, procedures in layer 3. No people's names and no numbers in a skill
  • Four files are one body: the ontology design document · CLAUDE.md · templates · skills. Change one and open the other three
