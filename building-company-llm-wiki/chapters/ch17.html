CHAPTER 17

품질을 코드로 지키기

규칙은 지키자고 말해서 지켜지지 않습니다

약 25분

솔빛테크가 볼트를 쓴 지 여섯 달째였습니다. 노트는 160개를 넘었고, 템플릿이 있고, CLAUDE.md가 있고, 예약 작업 세 개가 돌고 있었습니다. 김대표는 우리 볼트가 꽤 깨끗하다고 생각했습니다. 지킬 규칙이 몇 개 안 되고, 다들 성실했으니까요.

그러다 검증 스크립트를 처음 돌렸습니다. ERROR 19건이 나왔습니다.

놀란 것은 건수가 아니었습니다. 그 19건이 여섯 달 동안 한 번도 보고되지 않았다는 사실이었습니다. 링크가 끊긴 노트를 누군가는 분명히 열어봤을 텐데, 아무도 말하지 않았습니다.

이 장이 하는 일

4부에서 규칙을 정했고 5부에서 자동화를 걸었습니다. 이 장은 그 규칙이 실제로 지켜지고 있는지 확인하는 일을 사람의 성실함에서 떼어내 코드로 옮깁니다.

3장의 층위로 말하면, 1층 설계서에 적어둔 제약을 2층이 실제로 만족하는지 세는 장치입니다.

규칙 위반은 아무도 신고하지 않습니다

「점검은 다 같이 신경 씁시다」로 품질이 유지된 조직을 본 적이 없습니다. 게으르기 때문이 아닙니다. 구조가 그렇게 생겼습니다. 이유가 셋 있습니다.

첫째, 위반이 화면에 보이지 않습니다. 빠진 필드는 노트를 열어도 눈에 안 띕니다. 없는 것은 원래 안 보입니다. 잘못 적힌 status 값 하나도 그 노트만 보면 멀쩡합니다. 200개를 나란히 놓고 세어야 이상하다는 게 드러나는데, 사람은 200개를 나란히 놓지 않습니다.

둘째, 신고할 이유가 없습니다. 남이 쓴 노트의 잘못을 발견하면 선택지가 둘입니다. 「제가 고칠게요」는 내 일이 늘어나는 쪽이고, 「이거 틀렸어요」는 남을 지적하는 쪽입니다. 둘 다 부담이라서 대개는 세 번째 선택지를 고릅니다. 못 본 척하기입니다.

셋째, 대가를 다른 사람이 나중에 치릅니다. 마감 날짜를 비워둔 사람은 그날 아무 불편이 없습니다. 석 달 뒤에 대시보드의 빈칸을 보고 당황하는 사람이 대가를 치릅니다. 원인과 결과가 시간과 사람을 건너뛰면 학습이 일어나지 않습니다.

솔빛테크에서 실제로 이런 일이 있었습니다. 박사업이 제안서를 쓰다가 창고봇 노트에서 [[CAP-경로최적화]] 링크를 눌렀는데 빈 화면이 떴습니다. 노트 이름이 바뀌어 링크가 끊긴 것이었습니다. 그 사람은 검색으로 노트를 찾아 필요한 내용을 얻고, 제안서를 마저 썼습니다. 자기 일이 해결됐으므로 아무에게도 말하지 않았습니다. 같은 링크는 넉 달 뒤 첫 점검에서야 목록에 올라왔습니다.

이게 규칙 위반이 쌓이는 전형적인 방식입니다. 개인에게는 언제나 우회가 더 싸고, 우회는 흔적을 남기지 않습니다. 고쳐야 손해가 사라지는데, 고치지 않아도 그 사람의 손해는 사라집니다. 이 어긋남을 사람의 선의로 메우려는 시도가 지식관리에서 가장 자주 실패합니다.

「잘 관리하세요」는 관리 방법이 아닙니다

품질 계획이 「모두가 규칙을 잘 지킨다」로 되어 있으면 그건 계획이 아니라 희망입니다. 사람이 매주 노트 200개의 필드를 눈으로 대조하는 일은 둘째 주부터 안 합니다. 지루하고, 티가 안 나고, 안 해도 그 주에는 아무 일이 안 생기기 때문입니다.

스크립트는 지루함을 모릅니다. 그리고 안 돌면 티가 납니다. 리포트 파일이 그 주에 안 생기니까요.

무엇을 검사하나: 다섯 가지면 충분합니다

처음부터 정교하게 만들 필요가 없습니다. 아래 다섯 가지가 실제로 걸리는 문제의 대부분을 잡습니다.

검사무엇을 보나놔두면 벌어지는 일
필수 필드 누락 클래스마다 반드시 있어야 하는 필드가 채워졌는지 표와 대시보드에 빈칸이 생기고, AI가 그 빈칸을 그럴듯하게 메운다
통제 어휘 위반 status 값이 정해둔 목록 안에 있는지 「진행 중인 과제가 몇 개야」에 틀린 답이 나온다
끊어진 링크 위키링크가 가리키는 노트가 실제로 있는지 그래프에 구멍이 난다. 두 다리 건넌 질문이 답을 못 찾는다
오래된 노트 진행·운영 상태인데 30일 이상 그대로인 것 낡은 사실이 최신인 척한다. 가장 조용하고 가장 위험한 오염
금지 이름 사용 정본이 아닌 필드 이름이 쓰였는지 같은 뜻이 두 이름으로 갈려 집계가 소리 없이 틀린다

마지막 검사를 빠뜨리지 마세요. 뜻이 같은데 이름이 제각각이면 세는 일 자체가 불가능해집니다. 15장에서 간트 차트가 안 그려지는 이유로 들었던 바로 그 문제입니다. 아래 왼쪽 이름들은 볼트에 한 번도 등장하면 안 됩니다.

쓰면 안 되는 이름정본 이름뜻
deadline, 마감일due마감 날짜
uses_tech, tech_used, 사용기술pdm_uses이 노트가 쓰는 기술역량

다섯 가지의 공통점을 짚고 넘어가겠습니다. 전부 「사실인지 아닌지」가 아니라 「형식이 맞는지」를 봅니다. 창고봇이 쓰는 기술의 TRL이 4인지 6인지는 이 스크립트가 판단하지 않습니다. trl 칸이 비어 있는지만 봅니다. 이 책이 여러 번 꺼낸 그 사고, 작년 문서엔 TRL 4, 올해 문서엔 6이라 아무도 어느 쪽이 맞는지 모르는 상황은 코드가 풀 문제가 아닙니다. 코드가 하는 일은 그 값이 어느 노트에 적혀 있는지를 한자리에 모아, 사람이 30초 안에 확인하게 만드는 것까지입니다.

검증 스크립트 실물

파이썬만 있으면 됩니다. 외부 라이브러리를 하나도 쓰지 않았습니다. 볼트의 _ops/scripts/validate.py로 저장하시면 됩니다. 14장의 결정 트리로 보면 이건 경로 C, 판단이 아니라 계산이라 AI를 부르지 않는 쪽입니다.

코드를 옮겨 적기 전에 어디를 봐야 하는지 짚어 두겠습니다. 이 스크립트에서 정말 중요한 부분은 re도 pathlib도 아니라 맨 위의 REQUIRED와 STATUS_ENUM 두 묶음입니다. 그 둘은 1층 설계서를 그대로 옮겨 적은 것이고, 나머지 코드는 그걸 노트에 대조하는 기계일 뿐입니다. 설계서가 바뀌면 그 두 곳만 고칩니다. 규칙이 코드 여기저기에 흩어지면 반년 뒤에 아무도 못 고칩니다.

먼저 설정과 프론트매터 읽기입니다.

# _ops/scripts/validate.py
# 볼트 규칙을 코드로 확인한다. 외부 라이브러리 없음.

import re, sys, datetime
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]   # 볼트 최상위
TODAY = datetime.date.today()
STALE_DAYS = 30

# 클래스별 필수 필드. 1층 설계서와 이 표가 어긋나면 설계서가 정본이다.
REQUIRED = {
    "제품":     ["class", "id", "updated", "status", "owner", "since"],
    "기술역량": ["class", "id", "updated", "trl", "evidence"],
    "과제":     ["class", "id", "updated", "period", "funder", "budget"],
    "기회":     ["class", "id", "updated", "stage", "due"],
}

# status 어휘는 클래스마다 다르다. 전역 한 벌로 두면 오탐이 쏟아진다.
STATUS_ENUM = {
    "제품": {"기획", "개발", "운영", "중단"},
    "과제": {"기획", "진행", "검토", "완료", "보류"},
    "기회": {"기획", "진행", "검토", "완료", "보류"},
}

# 금지 이름. 뜻이 같은데 이름이 제각각이면 못 센다. 아래는 전부 나쁜 예다.
FORBIDDEN = {"deadline": "due", "마감일": "due",
             "uses_tech": "pdm_uses", "tech_used": "pdm_uses",
             "사용기술": "pdm_uses"}

findings = []
def add(level, where, msg):
    findings.append((level, where, msg))

FM = re.compile(r"\A---\n(.*?)\n---", re.S)

def frontmatter(text):
    m = FM.match(text)
    if not m:
        return None
    meta, key = {}, None
    for line in m.group(1).splitlines():
        if line.lstrip().startswith("-") and key:      # 목록 항목
            meta.setdefault(key, []).append(line.strip(" -").strip('"'))
            continue
        m2 = re.match(r"([A-Za-z_가-힣]+):\s*(.*)$", line)
        if m2:
            key = m2.group(1)
            val = m2.group(2).strip().strip('"')
            meta[key] = val if val else []
    return meta

다음이 검사 본체입니다. 노트 하나마다 다섯 가지를 봅니다.

notes = {p.stem: p for p in (ROOT / "Sources").rglob("*.md")}
LINK = re.compile(r"\[\[([^\]|#]+)")

for stem, path in sorted(notes.items()):
    where = path.relative_to(ROOT).as_posix()   # 파일명이 아니라 볼트 상대경로
    text = path.read_text(encoding="utf-8")
    meta = frontmatter(text)

    if meta is None:
        add("ERROR", where, "프론트매터 없음")
        continue

    cls = meta.get("class")
    if cls not in REQUIRED:
        add("ERROR", where, f"class 값이 설계서 목록 밖: {cls!r}")
        continue

    for field in REQUIRED[cls]:                       # 1. 필수 필드
        if not meta.get(field):
            add("ERROR", where, f"필수 필드 누락: {field}")

    st = meta.get("status")                            # 2. 통제 어휘
    if st and st not in STATUS_ENUM.get(cls, set()):
        add("ERROR", where, f"{cls}의 status 어휘 밖: {st!r}")

    for bad, good in FORBIDDEN.items():                # 3. 금지 이름
        if bad in meta:
            add("ERROR", where, f"금지 이름 {bad} 사용. {good} 로 바꿀 것")

    for target in set(LINK.findall(text)):             # 4. 끊어진 링크
        if target.strip() not in notes:
            add("ERROR", where, f"끊어진 링크: [[{target.strip()}]]")

    upd = meta.get("updated", "")                      # 5. 오래된 노트
    if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", str(upd)):
        add("ERROR", where, "updated 가 YYYY-MM-DD 형식이 아님")
    elif st in ("진행", "운영"):
        age = (TODAY - datetime.date.fromisoformat(upd)).days
        if age > STALE_DAYS:
            add("WARN", where, f"{age}일째 그대로 (status: {st})")

    if meta.get("confidence") == "draft":
        add("INFO", where, "사람 검토 대기")

마지막이 저장입니다. 결과를 사람이 아니라 다음 자동화가 읽게 남기는 것이 핵심입니다.

order = {"ERROR": 0, "WARN": 1, "INFO": 2}
findings.sort(key=lambda f: (order[f[0]], f[1]))
n = {lv: sum(1 for l, _, _ in findings if l == lv) for lv in order}

lines = [f"# 볼트 점검 {TODAY}", "",
         f"- ERROR {n['ERROR']} · WARN {n['WARN']} · INFO {n['INFO']}",
         f"- 검사한 노트 {len(notes)}개", ""]
for lv in ("ERROR", "WARN", "INFO"):
    group = [(w, m) for l, w, m in findings if l == lv]
    if not group:
        continue
    lines.append(f"## {lv} {len(group)}건")
    lines += [f"- `{w}` {m}" for w, m in group]
    lines.append("")

(ROOT / "_reports").mkdir(exist_ok=True)
(ROOT / "_reports" / f"점검-{TODAY}.md").write_text(
    "\n".join(lines), encoding="utf-8")

# 15장의 추이 그래프 재료. 한 줄씩 누적한다.
with (ROOT / "_reports" / "validate-history.csv").open(
        "a", encoding="utf-8") as f:
    f.write(f"{TODAY},{n['ERROR']},{n['WARN']},{n['INFO']},{len(notes)}\n")

sys.exit(1 if n["ERROR"] else 0)

마지막 줄의 sys.exit가 사소해 보이는데 그렇지 않습니다. ERROR가 있으면 0이 아닌 값으로 끝나므로, 나중에 이 스크립트를 다른 자동화 안에 넣었을 때 실패를 실패로 알아챕니다. 조용히 성공한 척하는 점검이 가장 나쁩니다.

이 스크립트가 일부러 하지 않는 세 가지

코드를 읽다 보면 「이것도 자동으로 고쳐주면 되지 않나」 싶은 자리가 몇 군데 있습니다. 일부러 안 한 것이라 이유를 적어 둡니다.

첫째, 아무것도 고치지 않습니다. 찾기만 합니다. 필드 하나를 자동으로 채우기 시작하면 곧 「비슷한 값으로 추측해서 채우는」 코드가 붙고, 그러면 볼트에 아무도 확인하지 않은 사실이 쌓입니다. 고치는 일은 14장의 예약 작업이 사람 승인 아래에서 합니다. 스크립트는 눈이고, 손은 따로 둡니다.

둘째, Sources/에 쓰지 않습니다. 읽기만 합니다. 이 원칙이 깨지면 새벽에 돌아간 스크립트가 만든 충돌본을 아침에 발견하게 됩니다. 6장에서 본 동기화 충돌이 그때 한꺼번에 옵니다.

셋째, 내용을 판단하지 않습니다. 「이 설명이 충분한가」, 「이 trl 값이 맞나」는 묻지 않습니다. 필드가 있는지 없는지, 값이 목록 안인지 밖인지만 봅니다. 판단이 들어가는 순간 오탐이 따라 들어오고, 오탐이 들어오면 뒤에서 볼 일이 벌어집니다.

ERROR와 WARN과 INFO를 가르는 기준

여기가 이 장에서 제일 중요한 절입니다. 스크립트를 짜는 일은 반나절이면 끝납니다. 어떤 위반을 ERROR로 올릴지 정하는 일은 그렇지 않습니다. 이 결정 하나가 검사의 수명을 정합니다.

한 문장 기준

ERROR 는 0이어야 하는 것만 넣습니다. 금요일 퇴근 전에 0으로 만들 자신이 없으면 그건 ERROR가 아닙니다.

등급뜻사람이 하는 일여기 넣는 것
ERROR 규칙 위반이 확실하다. 판단의 여지가 없다 그 주 안에 0으로 만든다 필수 필드 누락, class 오타, 어휘 위반, 끊어진 링크, 금지 이름
WARN 위반일 수도 있고 정상일 수도 있다 훑고 넘긴다. 쌓이면 그때 본다 30일 이상 방치, 마감 21일 이내, 필수는 아닌 빈 필드
INFO 위반이 아니다. 그냥 세는 것이다 아무것도 안 한다. 지표로만 쓴다 검토 대기 노트 수, 전체 노트 수, 클래스별 분포

WARN을 아예 안 보게 되면 그것대로 문제입니다. 그래서 규칙을 하나 둡니다. WARN 은 매주 보지 않고 분기에 한 번 몰아서 봅니다. 14장에서 자동화를 3개월마다 정리한다고 했는데 그때 같이 훑으면 됩니다. 그 자리에서 두 갈래가 납니다. 석 달 내내 같은 줄이 떠 있으면 그건 위반이 아니라 정상이니 검사를 지웁니다. 반대로 줄이 계속 늘고 있으면 ERROR로 올릴 때가 됐다는 신호입니다.

전부 ERROR로 만들면 어떻게 되는지는 정해져 있습니다. 첫 주에 ERROR 200건이 나옵니다. 사람은 200건을 못 고칩니다. 다음 주에도 200건입니다. 셋째 주에 그 리포트는 안 열립니다. 고칠 수 없는 숫자는 정보가 아니라 소음입니다. 14장에서 자동화가 죽는 방식이 멈춤이 아니라 소음이라고 했는데, 점검도 똑같이 죽습니다.

반대로 ERROR를 너무 좁게 잡으면 어떻게 될까요. 그건 별문제가 안 됩니다. WARN에 있던 검사를 나중에 ERROR로 올리면 되니까요. 등급을 옮기는 방향은 한쪽뿐입니다.

등급을 나누는 이유가 하나 더 있습니다. 목록의 길이를 사람이 감당하는 크기로 유지하는 것입니다. 어떤 볼트든 「이상해 보이는 것」은 수십 건씩 나옵니다. 그걸 전부 한 목록에 늘어놓으면 사람은 어디부터 봐야 할지 모릅니다. 등급은 위반의 심각도를 재는 자라기보다, 이번 주에 볼 것과 안 볼 것을 가르는 칸막이에 가깝습니다.

오탐 하나가 검사 전체를 죽입니다

검사를 만들다 보면 욕심이 납니다. 「내용이 부실한 노트도 잡자」, 「근거 없는 주장도 잡자」, 「제목이 성의 없는 것도 잡자」. 하지 마세요. 이 욕심이 점검을 망치는 가장 흔한 경로입니다.

솔빛테크가 검사 하나를 지운 이유

「본문이 300자 미만이면 부실 노트」라는 검사를 넣었습니다. 그럴듯했습니다. 그런데 결정 노트는 원래 짧습니다. 「지자체 공모에 참여한다. 실증 근거는 창고봇 기존 사이트를 쓴다」로 끝나는 노트가 정상인데, 그게 전부 걸렸습니다.

목록의 절반이 오탐이 되자 사람들은 목록을 훑는 대신 닫았습니다. 그 주에 진짜 ERROR 두 건도 같이 묻혔습니다. 검사 하나를 잘못 넣어서 나머지 검사가 전부 무력해진 것입니다.

사람은 목록을 항목 단위로 판단하지 않습니다. 목록 단위로 신뢰합니다. 열 줄 중 세 줄이 헛소리면 나머지 일곱 줄도 안 읽힙니다. 검사를 하나 늘려 얻는 이득보다 목록 전체의 신뢰를 잃는 손해가 훨씬 큽니다. 그래서 정밀도가 낮은 검사는 아예 만들지 않는 편이 낫습니다.

이 책을 만든 저장소에서도 같은 일이 있었습니다. 원고에 「세 가지」라고 써놓고 항목이 넷인 실수를 기계로 잡아보려 했습니다. 정규식으로 「세 가지」 뒤의 항목을 세는 검사였는데, 실측 일곱 건이 전부 오탐이었습니다. 「세 번째 주」 같은 서수와 「3개월」 같은 기간에 걸렸습니다. 그 검사는 지우고, 사람이 읽는 항목으로 옮겼습니다.

여기서 한 가지를 정해두면 판단이 쉬워집니다. 재현율과 정밀도 중 무엇을 포기할 것인가입니다. 재현율은 「놓치지 않는 정도」, 정밀도는 「걸린 것이 진짜인 정도」입니다. 둘 다 높으면 좋겠지만 현실에서는 한쪽을 올리면 다른 쪽이 내려갑니다.

품질 점검에서는 정밀도를 지키고 재현율을 포기합니다. 이유가 있습니다. 놓친 위반은 다음 주에 다시 걸릴 기회가 있습니다. 이 검사는 매주 도니까요. 그런데 한 번 신뢰를 잃은 목록은 다음 주에도 안 읽힙니다. 기회는 반복되고 신뢰는 반복되지 않습니다.

가르는 기준은 이렇습니다.

리포트에는 파일명이 아니라 볼트 상대경로를 적습니다

사소해 보이는데 실제로 당합니다. 회의록.md는 여러 폴더에 있고, 2026-07-15.md도 여러 폴더에 있습니다. 결과를 파일명으로만 기록하면 서로 다른 노트가 한 줄로 합쳐져 집계가 소리 없이 틀립니다.

앞의 코드에서 path.relative_to(ROOT).as_posix()를 쓴 까닭이 여기 있습니다. 리포트에는 Sources/40-Worklog/2026-07-15-주간회의.md처럼 볼트 최상위부터의 경로가 찍힙니다. 그래야 사람이 바로 그 파일을 엽니다.

주 1회, 사람이 잊어도 돌게

스크립트를 만들어놓고 손으로 돌리면 셋째 주부터 안 돌립니다. 14장에 이미 자리를 마련해 뒀습니다. 세 번째 예약 작업 「금요일 저녁 품질 점검」이 첫 줄에서 이 스크립트를 실행합니다. 전체 흐름은 이렇게 이어집니다.

왜 매일이 아니라 주 1회인가

스크립트는 매일 돌려도 비용이 들지 않습니다. 그런데 사람에게 매일 보여주면 안 됩니다. 이유가 둘입니다.

첫째, 고칠 시간을 줘야 합니다. 월요일에 본 ERROR를 화요일에 또 보여주면, 아직 고치는 중인 사람에게 같은 지적을 반복하는 셈이 됩니다. 두 번만 반복되면 그 알림은 잔소리가 되고, 잔소리는 꺼집니다.

둘째, 주 단위여야 증감이 뜻을 갖습니다. 하루 사이의 ERROR 증감은 대개 노이즈입니다. 어제 노트를 세 개 만들었으면 오늘 ERROR가 세 건 늘어 있습니다. 그건 나빠진 게 아니라 일한 흔적입니다. 주 단위로 보면 이 진동이 평평해집니다.

스크립트 자체는 14장의 안내대로 onlogon으로 매일 돌려 두어도 됩니다. 파일은 매일 쌓이고, 사람이 보는 것만 주 1회입니다. 그러면 추이 그래프의 점이 촘촘해지는 이득이 함께 옵니다.

  1. 파이썬이 셉니다

    경로 C입니다. 결과가 항상 같고 비용이 들지 않습니다. Windows 작업 스케줄러에 schtasks 한 줄로 걸어두거나, 아래 2번에 맡겨도 됩니다.

  2. 예약 작업이 읽고 해석합니다

두 폴더, 두 역할

자동화가 파일을 만들어도 되는 곳은 _reports/와 _moc/ 두 곳입니다. 나누는 기준은 간단합니다. _reports/는 날짜가 붙어 쌓이는 것, _moc/는 늘 최신 하나만 남는 것입니다. 점검 결과는 앞쪽, 대시보드는 뒤쪽입니다.

Sources/는 사람의 영역이고, 이 스크립트는 거기에 한 글자도 쓰지 않습니다. 읽기만 합니다.

볼트가 커지면 점검도 손봐야 합니다

노트가 몇백 개일 때는 이 스크립트가 1초 안에 끝납니다. 속도는 당분간 신경 쓸 일이 아닙니다. 대신 두 가지가 반드시 찾아옵니다.

검사에서 빼야 할 폴더가 생깁니다. _reports/ 아래에는 자동 생성물이 쌓이는데, 거기에 프론트매터를 기대하면 매주 ERROR가 수십 건씩 늘어납니다. 앞의 코드가 Sources/ 아래만 훑는 이유가 그것입니다. 90-Reference/의 원문 자료처럼 규칙을 적용하지 않기로 한 곳이 더 있다면 목록으로 만들어 설계서에 적어 두세요. 예외는 코드에 숨기지 말고 문서에 적습니다. 코드에만 있으면 반년 뒤에 아무도 이유를 모릅니다.

규칙이 바뀌면 과거 노트가 한꺼번에 걸립니다. 필수 필드를 하나 늘리면 그 주에 ERROR가 백 건이 됩니다. 규칙 자체는 옳은데 목록이 못 쓰게 됩니다. 그래서 필수 필드를 늘릴 때는 새 규칙을 WARN 으로 넣고, 과거 노트를 정리한 다음에 ERROR로 올립니다. 규칙을 바꾸는 일과 과거를 정리하는 일을 같은 주에 하지 마세요.

리포트가 3주 연속 안 열렸다면

점검은 도는데 아무도 안 보는 상태가 제일 나쁩니다. 시스템이 건강하다는 착각까지 얹어주기 때문입니다. 15장에서 대시보드를 아무도 안 열면 사람이 아니라 대시보드를 고치라고 했는데, 점검 리포트도 똑같습니다.

고칠 곳은 대개 길이입니다. ERROR 세 줄보다 WARN 마흔 줄이 먼저 나오면 안 읽힙니다. 맨 위 세 줄에 ERROR 건수와 지난주 대비 증감만 남기고 나머지는 아래로 내리세요.

이렇게 걸어두면 사람이 할 일은 하나만 남습니다. 월요일 아침에 ERROR 목록을 열고 그 주 안에 0으로 만드는 것. 1장에서 말한 「주간 점검 20분」이 여기서 진짜 20분이 됩니다. 노트 200개를 눈으로 대조하는 20분이 아니라, 이미 찾아 놓은 세 줄을 고치는 20분입니다. 점검을 자동화한다는 말은 사람이 손을 떼는 게 아니라, 사람이 쓰는 20분을 찾는 데서 고치는 데로 옮긴다는 뜻입니다.

# 지표는 개수가 아니라 비율로 남긴다
total = len(notes)
grounded = sum(1 for p in notes.values()
               if LINK.search(p.read_text(encoding="utf-8")))
reviewed = sum(1 for m in metas if m.get("confidence") == "reviewed")

add("INFO", "_", f"근거 있는 노트 {grounded}/{total}"

add("INFO", "_", f"검증된 노트 {reviewed}/{total}"

계산한 비율은 리포트 첫머리에 INFO 두 줄로 붙습니다. 사람은 매주 그 두 줄만 봐도 볼트가 어느 방향으로 가고 있는지 압니다.

마지막으로 시작 시점 이야기를 하겠습니다. 지표를 다섯 개 한꺼번에 켜지 말고 하나로 시작하세요. 첫 달에는 「검증된 노트 비율」 하나면 충분합니다. 이 숫자가 오르내리는 것을 보면서 무엇이 이 숫자를 움직이는지 감을 잡고, 그다음에 하나를 더합니다.

지표가 다섯 개면 매주 다섯 개가 움직이고, 그러면 어느 조치가 어느 숫자를 움직였는지 알 수 없습니다. 지표를 늘리는 일이 정보를 늘리는 일이 아니라 잡음을 늘리는 일이 되기 쉽습니다.

그리고 오늘 한 번은 재두세요. 여섯 달 뒤에 「좋아졌나요」라는 질문을 받는데, 그때 비교할 첫 숫자가 없으면 아무 말도 못 합니다. 19장에서도 같은 당부를 합니다. 측정은 시작할 때 시작해야 합니다.

사례 · 첫 점검의 ERROR 19건이 알려준 것

솔빛테크의 첫 실행 결과로 돌아가 봅니다. ERROR 19건이 나왔고, 김대표는 19개 노트를 고칠 준비를 했습니다. 그런데 목록을 원인별로 묶어 보니 대부분이 한 가지 원인이었습니다.

updated 필드가 없는 노트들이었고, 전부 12장의 템플릿을 만들기 전에 손으로 만든 노트였습니다. 그러니까 사람들이 규칙을 어긴 게 아니라, 규칙이 생기기 전에 만들어진 것들이었습니다.

그래서 고친 것은 노트가 아니었습니다. CLAUDE.md에 「새 노트는 반드시 템플릿에서 시작한다」를 한 줄 넣고, 옛 노트 열두 개는 파일 수정 시각으로 updated를 채웠습니다. 20분 걸렸습니다.

그 뒤로 ERROR는 3건 근처에서 오르내립니다. 0이 되지는 않았습니다. 새 노트를 만들면 며칠은 필드가 빕니다. 0이 아니라 「올라가지 않는 것」이 목표입니다. 노트가 늘어도 ERROR가 안 늘면 품질이 유지되고 있다는 뜻입니다.

덧붙여 놀란 것이 하나 있었습니다. 끊어진 링크 대부분이 노트 이름을 바꾼 흔적이었습니다. 옵시디언 안에서 이름을 바꾸면 링크가 따라오는데, 파일 탐색기에서 바꾸면 안 따라옵니다. 검사가 없었으면 그 습관을 영영 몰랐습니다.

잠깐, 정리!

  • 규칙 위반은 조용히 쌓인다. 보이지 않고, 신고할 이유가 없고, 대가를 다른 사람이 나중에 치르기 때문
  • 「잘 관리하세요」는 관리 방법이 아니다. 사람이 매주 노트 200개를 눈으로 대조하는 일은 둘째 주부터 안 한다
  • 검사 다섯 가지면 시작에 충분하다 필수 필드 누락 · 통제 어휘 위반 · 끊어진 링크 · 오래된 노트 · 금지 이름
  • 이 장의 핵심은 스크립트가 아니라 등급 설계다. ERROR 는 0이어야 하는 것만 넣는다
  • 전부 ERROR로 만들면 첫 주에 200건이 나오고, 셋째 주에 아무도 안 본다. 고칠 수 없는 숫자는 소음이다
  • 새 검사는 WARN 으로 시작해서 두 주 지켜본 뒤 올린다. 내리는 순서는 잘 안 된다
  • 오탐 하나가 목록 전체의 신뢰를 죽인다. 사람은 목록을 항목이 아니라 목록 단위로 믿는다
  • 답이 사람마다 다른 것은 코드에 넣지 않는다. 그게 곧 오탐이다
  • 리포트에는 파일명이 아니라 볼트 상대경로를 적는다. 같은 이름 파일이 합쳐지면 집계가 소리 없이 틀린다
  • 주 1회 자동 실행. 결과는 _reports/로 쌓고, 추이 한 줄은 _moc/의 대시보드로 흘려보낸다
  • 지표는 노트 수가 아니라 근거가 붙은 노트의 비율처럼, 지름길이 막힌 것만 고른다
  • WARN 은 매주 보지 않는다. 분기에 한 번 몰아서 보고 지울지 올릴지 정한다
  • 스크립트는 찾기만 한다. 고치는 일은 사람 승인 아래에서 예약 작업이 한다
  • ERROR의 목표는 0이 아니라 올라가지 않는 것이다
