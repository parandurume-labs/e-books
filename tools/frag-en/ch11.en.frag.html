By the end of Chapter 10 the design document is finished. One file, _ops/01-ontology-design.md, holds the classes, the predicates, the fields and the vocabulary.

And the AI has never read it.

What this chapter builds

One CLAUDE.md file at the top of the vault. It holds the rules AI has to follow in this vault. In the four-layer model from Chapter 3 it is the first piece of layer 3 machinery, and from here on you are not designing rules but running them.

The full text is at the end of the chapter, ready to copy. Change the company name and it runs today.

How one file spreads to the whole team

What makes this approach good is not that it does anything clever. It is that distribution and updating take care of themselves.

The vault already sits in a Teams shared folder (Chapter 6). So put this file at the top of the vault and the same file lands on every machine on the team. A new joiner gets the same rules the moment they connect the vault. Changing a rule means changing one place.

Getting the AI to read the file is simple. Add one line to the folder instructions you wrote when connecting the vault in Chapter 7.

Before starting any work, read CLAUDE.md at the top of the vault,
and apply the rules written there to every task in this folder.

There is a bonus. This file also reads sensibly to a person. Explaining "what we hold to when handling company material" to a new joiner used to cost a colleague 30 minutes. Now you point them at the file. The key-person risk that worried Chapter 1 drops a layer here, because the rules came down out of someone's head into a file.

As of July 2026 this is the most reliable approach. Some tools pick up instruction files on their own, but writing one line down beats trusting behavior you have not verified. How to verify is in the exercise at the end of this chapter.

What goes in this file and what does not

Once the file exists you will want to put everything in it. That turns into a ten-page document quickly, and nobody follows a ten-page document. The vault already has four places for rules, and each one takes a different job.

WhereWhat goes thereExample

One test divides them. "Does this rule bind every task, or only one task?" A rule that applies only when tidying meeting notes goes down into a skill. Only what has to hold whether you are writing a proposal, making a note, or running a job at three in the morning stays in CLAUDE.md.

A little overlap with the design document is fine. Vocabulary lists can live in both. But when you change a definition, change the design document first and this file second. Without a fixed order the two files drift apart.

How to write an absolute rule

Anyone who has written rules knows most of them go unfollowed. The rules that go unfollowed have something in common.

Bad rule

"Write reliably, referring accurately to our company material"

Good rule

"Use only notes under Sources/ as evidence. For a number that is not in a note, write 확인 필요. Name the evidence note at the end of each paragraph."

Four things separate them.

  1. Write it as "do not"

    "Be accurate" specifies no action. "Do not write a number that is not there" does. A prohibition has a clear boundary, so whether it was broken is decidable.

  2. Write it so a breach is checkable

    The best rule is one the check script in Chapter 17 verifies mechanically. "A project note's status is one of the five agreed values" is checkable. "Reliably" has no method of verification.

  3. One judgment per rule

    "Write accurately and concisely, cite evidence, and mask confidential material" is not one rule but four. Bundled that way, keeping one of the four looks like keeping the rule.

  4. Never write "if possible" or "where practical"

    The moment those words attach, it stops being a rule and becomes a preference. If you truly need an exception, state the exception. Like "mask names in confidential notes, except in internal meeting material."

Written to that standard, two absolute rules form this book's spine. Everything else is a variation on those two.

These two lines are the whole thing

1. Never fill in a fact that is missing. If it is not in the vault, answer "no record".

2. For a number with no evidence, write 확인 필요. Do not put in a plausible value.

Hallucination mostly starts at a blank, because a blank invites filling. So you need a rule that explicitly gives permission to leave a blank blank.

The second rule has a bonus. As places marked 확인 필요 pile up in the vault, they become a list of what needs filling in. The dashboard in Chapter 15 counts them and shows them. Leave blanks honestly and the system finds the blanks for you.

What the other four lines do

The full text below carries six absolute rules. You have seen the first two. The other four each stop one accident that actually happened.

RuleThe accident it stops
Name the evidence note alongside the answerAn answer looks right, but checking it means digging through the vault from scratch. Then review takes longer than the original work, and three weeks later that automation gets switched off
Report contradictions, do not fix themWhen the AI quietly picks a side, the fact that there was a contradiction disappears. Which side is right is something a person knows
Never guess a person's name or titleIt ties "Lee CEO" and "Kim CEO" together as one person, or invents someone who does not exist. A document with a wrong name loses trust in one go

Those six lines are the longest-lived part of the file. The other sections differ by company and change from year to year, but these six go through almost unchanged.

The list of facts you keep getting wrong

This is the most useful section in the chapter. It is also the one other guides rarely cover.

The two rules above deal with blanks. But a company has a more dangerous place. Not a blank, but a box where two values are written. Here the AI does not invent anything. It uses a value genuinely present in the vault. It just picks one of the two. People do exactly the same.

Solbit Tech in practice: TRL 4 and TRL 6

Solbit Tech has one accident that has repeated for years. WareTwin's TRL differs from document to document. Some material says 4, some says 6, and nobody was sure which was right.

It got settled in the weekly meeting on 15 July 2026. "4 is right. The 6 was overstated." The correction went into the meeting note and became the decision note DEC-2026-0715-TRLCorrection.

But the old proposal files are still sitting in the vault. Nor should they have been deleted. Those are documents you keep exactly as submitted. So when the AI reads one of those files, it still sees 6.

Rules alone cannot stop this. Follow "never fill in a fact that is missing" perfectly and 6 is still a fact that is in the vault.

So CLAUDE.md gets one more section. "Facts about us that are easy to get wrong." It nails down which side is right.

Three things to hold to when you build this list.

  • Add one line per accident. Do not fill it in from imagination. One line is one accident, and accidents you have not had are hard to predict.
  • Write the evidence alongside. Write only "TRL is 4" and in six months nobody knows who decided that or why. Then the line wobbles again.
  • Do not go past ten lines. Past that it is not a rules problem. Your vault is untidy.

This list is a stopgap

Every time a line gets added, ask this. "Is this a line I could remove by fixing a note?"

WareTwin's TRL cannot go. The old proposal files have to stay. But "Pickview has no pilot data" can go by putting one line, evidence: none. 확인 필요, into the Pickview note. Remove the removable lines by fixing layer 2, and leave only the ones you cannot remove.

Covering something with a rule is not a real cure. But a proposal has to go out today, so you cover it now and fix it later.

Finding lines for the list before the accident

Waiting to be burned by every accident is a waste of time. For the first pass, sweeping the vault for values that disagree gets you started faster. That may sound like the imagining I just warned against. It is not. It is pulling out disagreements the vault already contains.

Read every note under Sources/ and find places where the same subject
carries different values.

Look for:
- different numbers for the same product or technology (TRL, dates, amounts, rates)
- the same company or person written under different names
- the same fact described differently in two notes

Rules:
- Change nothing. Report as a table only.
- For each item, name the file and what it says.
- Do not judge which side is right. A person judges.

Then a person goes down the result table line by line. Split it into what you remove by fixing a note and what you cannot remove and so keep on the list. Solbit Tech spent an hour on this and got eleven items. Nine went away by fixing notes, and two were added to the list above.

How to run this check on a schedule is in the risk scan in Chapter 16 and the validation script in Chapter 17. Here you run it once, to build the first version.

The one box that separates reviewed from draft

Chapter 10 put confidence on the field list. It has only two values.

ValueMeaningWho sets itWhere it can be used
draftAI wrote a first pass and no person has looked at italways, when AI makes a noteinternal reference only
revieweda person has checked itpeople onlyproposals, reports, external documents

The rules run three lines. A note AI makes starts as draft, without exception. AI never turns draft into reviewed. A draft note is never cited in an external document. That last line comes back in the Chapter 14 automation.

You will ask why only two values. Add a middle value like "in review" and everything piles up in the middle. Most states are awkward to call definitely right and awkward to call wrong. Then the box distinguishes nothing. With two, a person has to make a call, and forcing that call is the point of the box.

One more line is worth adding. A note built from uncertain statements, the "apparently" and "seems to be" kind, stays draft. Meeting notes are full of that phrasing, and once structured the uncertainty vanishes into flat assertions. You are moving the original hedging into the confidence box.

This one box becomes the "share of verified notes" metric in Chapter 15, and the graph of that share rising becomes the evidence in your rollout report. Unless the fact that a person checked is recorded somewhere, you cannot count it. Chapter 12 carries on with how to run it.

Where automation may create files

This is the rule to nail down hardest. Once AI starts writing files into the vault, where it writes is everything.

FolderMay automation create files?Why
_reports/YesCheck results and reports. Derivatives, not human knowledge
_moc/YesDashboards and map notes. Rebuildable at any time
Sources/Only after a person approvesWhere company facts live. All of layer 2 is here
_ops/People onlyThe rules themselves. Grant permission to edit the rules and they are not rules

Automation may create files on its own in two places, _reports/ and _moc/. Write down only one of them and the dashboard in Chapter 15 becomes a rule violation, and that kind of mismatch sits quietly until it turns into another argument about which side is right.

When creating or editing notes under Sources/, show a table first and get approval. The meeting-note structuring in Chapter 16 runs on exactly this pattern.

A day comes when this feels tedious. "It does a good job anyway, can we not just let it write everything?" Work out the cost of undoing it once and you have your answer. When the AI makes ten notes and three are wrong, finding which three takes far longer than approving them would have. And wrong notes become the evidence for the next question, which produces another wrong answer. Contaminate layer 2 and everything stacked on top wobbles.

Never let AI edit the rules file itself

It looks convenient. Say "tidy up these rules" and the sentences come back cleaner. But do that a few times and you lose track of when a line you added disappeared. In the tidying, "without exception" becomes "where possible," and that one word kills the rule.

_ops/ and CLAUDE.md are edited by people only. You can still ask AI for suggestions. "Find cases where this rule was broken and suggest a better wording" is the safe limit. A person applies the change.

- New notes carry confidence: draft and updated set to today's date (KST).

The week after building this file, Solbit Tech re-ran the exact three questions that opened this chapter.

It was not perfect, though. Once, it created a note under Sources/ first and reported afterwards. Section 3 did not hold that time. That is why the check script in Chapter 17 exists. Rules raise the odds a great deal. They do not get you to 100%.

When the rules go unfollowed

Let me be honest. Even with this file, the rules will not be followed 100% of the time. Instructions are a strong recommendation, not enforcement. Better to set your expectations accurately from the start.

SymptomUsual causeFix
It seems unaware of the rules entirelyit did not read the filecheck the "read this first" line in the folder instructions
It follows only the early partsthe file is longdelete the unused items, not the unfollowed ones
Some days it holds, some days it does nottwo rules contradict each otherfind the conflicting pair and merge them, or give them an order
It follows loosely"where practical" or "if possible" crept indelete the words or state the exception

Loosening the rules because "no record" keeps coming back

This arrives around week three, guaranteed. Everything you ask returns "no record" and it gets frustrating. Then someone says it. "Rule 1 means it never answers anything. Should we loosen it?"

Loosen it here and the system collapses. "No record" is a sign the rule is working, not a sign it is broken. It means the vault is still empty. What needs fixing is layer 2, not the rules.

Use the first line of section 6 instead. With "say which note the fact should be written into" in place, every "no record" hands you the name of the next note to make. Do that for two weeks and answers start coming.

The second row matters most. When rules go unfollowed you want to write more rules, and the longer it gets the less it is followed. One test is enough. "Has an accident ever happened because this line was missing?" If not, delete it. Rules you imagined bury the rules you actually need.

The third row catches people often too. Conflicting pairs are usually hard to spot. The pair Solbit Tech hit was this. "Answer with a table and do not pad it out" against "name the evidence note alongside the answer." Answering concisely means dropping the evidence, and writing all the evidence makes it long. Some days it went one way, some days the other.

The fix is not to delete one of them but to give them an order. The last line of section 0 does that job. "When rules conflict, the lower number wins." The evidence rule is in section 1 and the concision rule is in section 6, so evidence wins. Number your rules and that one line settles every conflict.

Do not try to stop things with a single rule

The more important something is, the more you stop it with structure. Structure beats a line of rules.

"Do not use confidential material" is one line of rules. Layer on the confidential field (Chapter 10), write-after-approval (Chapter 16), the weekly check script (Chapter 17) and the violation count on the dashboard (Chapter 15), and you have four layers. One layer gets through and the rest catch it.

Rules, verification and visibility come as a set. With rules but no verification, you do not even know whether the rules are being followed.

One last thing. When you change a rule, record why. The edit date and the maintainer at the top of the file are not enough. If an accident made you add a line, record that accident as a decision note in 40-Worklog/ and link it beside the rule as evidence. Then, when someone asks six months later "why is this line here, shall we delete it," you have an answer.

Attaching evidence to rules brings one more thing with it. It separates the lines you may delete from the lines you may not. A line with no evidence link is usually one you imagined, and deleting those first shortens the file without weakening it.
