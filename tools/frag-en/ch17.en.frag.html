Solbit Tech was six months into using the vault. There were more than 160 notes, there were templates, there was a CLAUDE.md, and three scheduled tasks were running. Kim, the CEO, thought the vault was fairly clean. There were only a handful of rules to keep, and everyone was conscientious.

Then they ran the validation script for the first time. It reported 19 ERRORs.

The count was not the surprising part. The surprising part was that not one of those 19 had been reported in six months. Somebody must have opened a note with a broken link. Nobody said anything.

What this chapter is for

Part 4 set the rules and Part 5 put automation on top of them. This chapter takes the job of confirming that those rules actually hold away from human diligence and moves it into code.

In the layers from Chapter 3, it is the device that counts whether layer 2 really satisfies the constraints you wrote into the layer 1 design doc.

Nobody reports a rule violation

I have never seen an organization keep quality with "let's all pay attention to the checks". Not because people are lazy. The structure makes it happen. There are three reasons.

First, a violation is not visible on screen. A missing field does not catch your eye when you open the note. Absence is invisible by nature. One wrongly written status value looks fine as long as you are only looking at that note. It takes lining up 200 notes side by side for the oddity to show, and nobody lines up 200 notes.

Second, there is no reason to report it. Find a mistake in somebody else's note and you have two options. "I'll fix it" adds to your own workload, and "this is wrong" points a finger at a colleague. Both cost something, so most people take a third option. Look away.

Third, somebody else pays for it later. The person who left the due date blank feels nothing that day. The person who pays is whoever stares at an empty cell in the dashboard three months later. When cause and effect skip across time and across people, no learning happens.

This actually happened at Solbit Tech. Park, who handles sales, was writing a proposal and clicked the [[CAP-RouteOptimization]] link in the Warebot note. A blank screen came up. The note had been renamed and the link had broken. Park searched for the note, got what he needed, and finished the proposal. His own problem was solved, so he told nobody. That same link did not appear on any list until the first check four months later.

Rule violations pile up like that. For the individual, working around it is always cheaper, and working around it leaves no trace. Fixing it removes the cost, but so does not fixing it, at least for that person. Trying to close that gap with goodwill is the most common way knowledge management fails.

"Manage it well" is not a management method

If your quality plan reads "everyone keeps the rules", that is not a plan, it is a hope. Nobody eyeballs 200 notes' worth of fields every week past the second week. It is dull, it is invisible, and skipping it costs nothing that week.

A script does not get bored. And when it stops running you notice, because the report file does not appear that week.

What to check: five is enough

You do not need something sophisticated on day one. The five below catch most of what actually goes wrong.

CheckWhat it looks atWhat happens if you leave it
Missing required field Whether the fields each class must carry are filled in Blank cells appear in tables and dashboards, and the AI fills those blanks with something plausible
Controlled vocabulary violation Whether the status value is in the list you fixed "How many projects are in progress" comes back wrong
Broken link Whether the note a wikilink points at actually exists The graph gets holes. Two-hop questions cannot find an answer
Stale note Anything in 진행 or 운영 that has sat untouched for 30 days or more Old facts pass themselves off as current. The quietest and most dangerous kind of pollution
Forbidden name Whether a non-canonical field name got used One meaning splits across two names and your counts go quietly wrong

Do not skip that last one. When the same meaning is written under all different names, counting becomes impossible. It is exactly the problem Chapter 15 blamed for the gantt chart not drawing. The names on the left below should never appear in your vault.

Never use theseCanonical nameMeaning
deadline, due_datedueThe due date
uses_tech, tech_used, used_techpdm_usesThe capability this note draws on

Notice what the five have in common. Every one of them asks whether the form is right, not whether the content is true. Whether the TRL of the technology Warebot uses is 4 or 6 is not something this script decides. It only looks at whether the trl box is empty. Think back to the accident this book keeps returning to: TRL 4 in last year's document, 6 in this year's, and nobody knowing which is right. That is not a problem code can solve. What code does is gather which note each value is written in, in one place, so a person can settle it in 30 seconds.

Before that: install Python and run it once

This section is for anyone who has never opened a command prompt. Skip it if you already use Python.

  1. Install Python

    Get the Windows installer from python.org. On the first screen there is a checkbox at the bottom, "Add python.exe to PATH". Tick it before you install. Leave it off and you get exactly the error at the top of Appendix C.

  2. Save the file inside the vault

    Join the code below together and save it as _ops/scripts/validate.py. That is the folder you made in Chapter 7.

  3. Run it with one line

    Type cmd in the Start menu and the command prompt appears. Put py "C:\path\_ops\scripts\validate.py" in and press Enter. Get the path by right-clicking the file in Explorer and choosing "Copy as path".

  4. Check the result in a file, not on screen

    If nothing prints, it worked. Look in the vault's _reports/ folder for a file with today's date on it. If that file is there, it ran properly.

You never have to open a command prompt at all

The default route in this book is to hand it to Cowork. The third scheduled task in Chapter 14 already owns this work: its first line says "run _ops/scripts/validate.py". Typing run _ops/scripts/validate.py and summarize the result into the chat window does the same thing.

So step 3 above is worth doing once, to narrow down a cause when something breaks, and no more.

The validation script itself

Python is all you need. It uses no external libraries. Save it as _ops/scripts/validate.py in the vault. On the decision tree from Chapter 14 this is route C: calculation rather than judgment, so no AI is involved.

Before you copy the code out, here is where to look. The parts that matter in this script are not re or pathlib but the three blocks at the top: REQUIRED, STATUS_ENUM and FORBIDDEN. Those three are the layer 1 design doc transcribed, and the rest of the code is just a machine that holds notes up against them. When the design doc changes, you edit those three places only. Scatter the rules through the code and nobody can change them six months from now.

First, the configuration and the frontmatter reader.

# _ops/scripts/validate.py
# Check the vault rules in code. No external libraries.

import re, sys, datetime
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]   # top of the vault
TODAY = datetime.date.today()
STALE_DAYS = 30

# Required fields per class. If this table and the layer 1 design doc
# disagree, the design doc wins.
# class, id and updated are required everywhere. The rest varies by class.
REQUIRED = {
    # the four backbone classes from Chapter 9
    "제품":     ["class", "id", "updated", "status", "owner", "since"],
    "기술역량": ["class", "id", "updated", "trl", "evidence"],
    "과제":     ["class", "id", "updated", "period", "funder", "budget"],
    "기회":     ["class", "id", "updated", "stage", "due"],
    # the three support classes from Chapter 9
    "조직":     ["class", "id", "updated"],
    "사람":     ["class", "id", "updated"],
    "결정":     ["class", "id", "updated", "date"],
    # Not classes. These are note kinds inside 40-Worklog. See Chapter 12.
    # Leave them out and you get a flood of "class value not in the
    # design doc list" ERRORs, so they are listed here too.
    "회의록":   ["class", "id", "updated", "date"],
    "업무로그": ["class", "id", "updated", "owner"],
}

# The status vocabulary differs by class. One global set gives you
# a flood of false positives.
STATUS_ENUM = {
    "제품": {"기획", "개발", "운영", "중단"},
    "과제": {"기획", "진행", "검토", "완료", "보류"},
    "기회": {"기획", "진행", "검토", "완료", "보류"},
}

# Forbidden names. One meaning under all different names cannot be
# counted. Every name on the left is a bad example.
FORBIDDEN = {"deadline": "due", "due_date": "due",
             "uses_tech": "pdm_uses", "tech_used": "pdm_uses",
             "used_tech": "pdm_uses"}

findings = []
metas = []                                   # the metrics below use this list
def add(level, where, msg):
    findings.append((level, where, msg))

FM = re.compile(r"\A---\n(.*?)\n---", re.S)

def frontmatter(text):
    m = FM.match(text)
    if not m:
        return None
    meta, key = {}, None
    for line in m.group(1).splitlines():
        if line.lstrip().startswith("-") and key:      # a list item
            meta.setdefault(key, []).append(line.strip(" -").strip('"'))
            continue
        m2 = re.match(r"([A-Za-z_가-힣]+):\s*(.*)$", line)
        if m2:
            key = m2.group(1)
            val = m2.group(2).strip().strip('"')
            meta[key] = val if val else []
    return meta

Next is the body of the check. It looks at five things per note.

notes = {p.stem: p for p in (ROOT / "Sources").rglob("*.md")}
LINK = re.compile(r"\[\[([^\]|#]+)")

for stem, path in sorted(notes.items()):
    where = path.relative_to(ROOT).as_posix()   # vault-relative path, not filename
    text = path.read_text(encoding="utf-8")
    meta = frontmatter(text)

    if meta is None:
        add("ERROR", where, "no frontmatter")
        continue

    metas.append(meta)                             # collected here for the metrics

    cls = meta.get("class")
    if cls not in REQUIRED:
        add("ERROR", where, f"class value not in the design doc list: {cls!r}")
        continue

    for field in REQUIRED[cls]:                       # 1. required fields
        if not meta.get(field):
            add("ERROR", where, f"missing required field: {field}")

    st = meta.get("status")                            # 2. controlled vocabulary
    if st and st not in STATUS_ENUM.get(cls, set()):
        add("ERROR", where, f"status outside the {cls} vocabulary: {st!r}")

    for bad, good in FORBIDDEN.items():                # 3. forbidden names
        if bad in meta:
            add("ERROR", where, f"forbidden name {bad}. use {good} instead")

    for target in set(LINK.findall(text)):             # 4. broken links
        if target.strip() not in notes:
            add("ERROR", where, f"broken link: [[{target.strip()}]]")

    upd = meta.get("updated", "")                      # 5. stale notes
    if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", str(upd)):
        add("ERROR", where, "updated is not in YYYY-MM-DD form")
    elif st in ("진행", "운영"):
        age = (TODAY - datetime.date.fromisoformat(upd)).days
        if age > STALE_DAYS:
            add("WARN", where, f"unchanged for {age} days (status: {st})")

    if meta.get("confidence") == "draft":
        add("INFO", where, "waiting for human review")

Last comes saving. The point is to leave the result for the next automation to read, not for a person. One thing to know in advance: the code below uses the two metric values (total and reviewed) built in the last section of this chapter. When you copy it into a file, put that section's code above this one.

order = {"ERROR": 0, "WARN": 1, "INFO": 2}
findings.sort(key=lambda f: (order[f[0]], f[1]))
n = {lv: sum(1 for l, _, _ in findings if l == lv) for lv in order}

lines = [f"# Vault check {TODAY}", "",
         f"- ERROR {n['ERROR']} · WARN {n['WARN']} · INFO {n['INFO']}",
         f"- notes checked: {len(notes)}", ""]
for lv in ("ERROR", "WARN", "INFO"):
    group = [(w, m) for l, w, m in findings if l == lv]
    if not group:
        continue
    lines.append(f"## {lv} {len(group)}")
    lines += [f"- `{w}` {m}" for w, m in group]
    lines.append("")

(ROOT / "_reports").mkdir(exist_ok=True)
(ROOT / "_reports" / f"check-{TODAY}.md").write_text(
    "\n".join(lines), encoding="utf-8")

# Raw material for the Chapter 15 trend chart. One line per run.
# Columns: date, ERROR, WARN, INFO, total notes, reviewed share (%)
# The last column is the line Chapter 15 draws. Without it, no chart.
with (ROOT / "_reports" / "validate-history.csv").open(
        "a", encoding="utf-8") as f:
    f.write(f"{TODAY},{n['ERROR']},{n['WARN']},{n['INFO']},"
            f"{len(notes)},{reviewed * 100 // total}\n")

sys.exit(1 if n["ERROR"] else 0)

That sys.exit on the last line looks trivial and is not. With any ERROR the script ends on a non-zero value, so when you later wrap this script inside another automation, a failure registers as a failure. A check that quietly pretends to succeed is the worst kind.

Three things this script deliberately does not do

Reading the code you will hit a few spots where you think "why not just fix that automatically". Those are deliberate, so here are the reasons.

First, it fixes nothing. It only finds. Start auto-filling one field and code that "guesses a similar value" follows soon after, and then facts nobody has checked start accumulating in the vault. Fixing is the job of the Chapter 14 scheduled task, under human approval. The script is the eyes. Keep the hands separate.

Second, it does not write to Sources/. It only reads. Break that principle and one morning you will find the conflict copies that a script made at 3am. Every sync conflict from Chapter 6 arrives at once.

Third, it does not judge content. It never asks "is this explanation good enough" or "is this trl value right". It looks at whether a field is there and whether a value is inside the list. The moment judgment enters, false positives come in with it, and false positives cause what comes next.

Where the line between ERROR, WARN and INFO goes

This is the most important section in the chapter. Writing the script takes half a day. Deciding which violations count as ERROR does not. That one decision sets how long the check survives.

The one-sentence rule

Only put things in ERROR that have to be zero. If you are not confident you can drive it to zero before you leave on Friday, it is not an ERROR.

LevelWhat it meansWhat a person doesWhat goes here
ERROR A definite rule violation. No room for judgment Drive it to zero that week Missing required field, class typo, vocabulary violation, broken link, forbidden name
WARN Might be a violation, might be normal Skim and move on. Look properly when it piles up Untouched for 30 days or more, due within 21 days, an empty field that is not required
INFO Not a violation. Just a count Nothing. It is only a metric Notes awaiting review, total notes, distribution by class

Never looking at WARN is a problem of its own, so set one rule. You do not read WARN weekly. You read it once a quarter, all at once. Chapter 14 said to tidy your automations every three months, and this fits in the same slot. The review forks two ways. If the same line has sat there for three months it is normal rather than a violation, so delete the check. If instead the lines keep multiplying, that is the signal to promote it to ERROR.

What happens if you make everything an ERROR is entirely predictable. Week one gives you 200 ERRORs. No person fixes 200 items. Week two gives you 200 again. In week three the report goes unopened. A number you cannot act on is noise, not information. Chapter 14 said automation dies of noise rather than of stopping, and a check dies the same way.

What if you draw ERROR too narrowly instead? That barely matters. You can promote a check from WARN to ERROR later. Levels only move in one direction.

There is one more reason for having levels. They keep the list at a length a person can carry. Every vault produces dozens of things that "look odd". Lay them all out in one list and nobody knows where to start. A level is less a ruler for how serious a violation is and more a partition between what you look at this week and what you do not.

One false positive kills the whole check

Build a few checks and you get greedy. "Let's catch thin notes too", "let's catch unsupported claims", "let's catch lazy titles". Do not. That greed is the most common route to ruining the check.

Why Solbit Tech deleted one check

They added a check that flagged "a body under 300 characters is a thin note". It sounded sensible. But decision notes are short by nature. A note that ends with "we are entering the city government call. we use Warebot's existing sites as the validation evidence" is a perfectly normal one, and every last one of them got flagged.

Once half the list was false positives, people stopped skimming the list and started closing it. Two real ERRORs that week went down with it. One badly chosen check made every other check useless.

People do not judge a list item by item. They trust it list by list. If three lines out of ten are nonsense, the other seven go unread too. The damage of losing trust in the whole list far outweighs the gain from one extra check. So a check with low precision is better not built at all.

The same thing happened in the repository that produced this book. The manuscript sometimes says "three things" and then lists four, and we tried to catch that by machine. The check counted items after the phrase "three things" with a regular expression, and all seven hits we measured were false positives. It tripped on ordinals like "the third week" and durations like "three months". We deleted the check and moved it into the list a person reads.

Settling one question up front makes these calls easier. Which do you give up, recall or precision? Recall is "how little you miss", precision is "how much of what you caught is real". Both high would be lovely, but in practice raising one lowers the other.

In a quality check you protect precision and give up recall. There is a reason. A missed violation gets another chance next week, because this check runs every week. A list that has lost your trust once will not be read next week either. Chances repeat. Trust does not.

Here is where the line falls.

What code is good atWhat a person has to do
Whether a field is thereWhether this note explains enough
Whether a value is in the listWhether this status matches reality
Whether a link points at a real fileWhether making this link was the right call
Whether a date fits the formatWhether this deadline is realistic

The questions on the left have exactly one answer. The ones on the right differ from person to person. Put something whose answer varies by person into code and that is your false positive.

Write vault-relative paths in the report, not filenames

It looks trivial and it catches people. meeting-note.md lives in several folders, and so does 2026-07-15.md. Record results by filename alone and different notes merge into one line, and your counts go quietly wrong.

That is why the code above uses path.relative_to(ROOT).as_posix(). The report prints paths from the top of the vault down, like Sources/40-Worklog/2026-07-15-weekly-meeting.md. That way a person opens the right file straight away.

Once a week, running even when people forget

Build the script and run it by hand and you stop running it in week three. Chapter 14 already made room for it. The third scheduled task, "Friday evening quality check", runs this script on its first line. Look first at why the cycle is weekly, then at the four steps of the whole flow.

Why weekly rather than daily

Running the script daily costs nothing. Showing it to a person daily is a mistake. Two reasons.

First, people need time to fix things. Show an ERROR on Monday and show it again on Tuesday and you are repeating the same criticism to somebody who is still working on it. Two repeats turn the alert into nagging, and nagging gets switched off.

Second, a change only means something at weekly scale. Day-to-day ERROR movement is mostly noise. Make three notes yesterday and today's ERROR count is three higher. That is not decay, it is evidence of work. At weekly scale the wobble flattens out.

The script itself can run daily on onlogon, as Chapter 14 describes. The files pile up daily and only the human viewing is weekly. You get a denser trend chart for free that way.

  1. Python counts

    Route C. The result is always the same and it costs nothing. Put it in Windows Task Scheduler with one schtasks line, or leave it to step 2 below.

  2. The scheduled task reads and interprets

    Route A. It fixes only the mechanically certain ERRORs and leaves anything needing a judgment about the facts on the list untouched. It touches no field on a confidence: reviewed note.

  3. The result lands in two places

    The report a person reads goes to _reports/check-2026-07-31.md, and the single trend line goes to _reports/validate-history.csv.

  4. The dashboard picks that line up

    The Chapter 15 weekly dashboard reads the csv and redraws the trend line in _moc/000-dashboard.md. On Monday a person looks at that one page.

Two folders, two roles

Automation may create files in two places, _reports/ and _moc/. The rule for splitting them is simple. _reports/ is for things that accumulate with a date on them, _moc/ is for things where only the latest one survives. Check results go in the first, the dashboard in the second.

Sources/ is human territory, and this script does not write a single character there. It only reads.

A bigger vault needs a reworked check

At a few hundred notes this script finishes in under a second. Speed is not your concern for a long while. Two other things will definitely arrive.

Folders that have to be excluded appear. Generated output piles up under _reports/, and expecting frontmatter there adds dozens of ERRORs a week. That is why the code above only sweeps under Sources/. If there are more places where you decided not to apply the rules, like the source material in 90-Reference/, make a list and write it into the design doc. Do not hide exceptions in code. Write them in a document. Kept only in code, nobody knows the reason six months later.

Change a rule and every old note trips at once. Add one required field and that week brings a hundred ERRORs. The rule itself is right and the list becomes unusable. So when you add a required field, put the new rule in as a WARN, clean up the old notes, and only then promote it to ERROR. Do not change a rule and tidy the past in the same week.

If the report has gone unopened three weeks running

A check that runs and nobody reads is the worst state, because it also hands you the illusion that the system is healthy. Chapter 15 said that if nobody opens the dashboard you fix the dashboard rather than the people, and the check report works the same way.

What usually needs fixing is length. Forty lines of WARN in front of three lines of ERROR will not be read. Leave the ERROR count and the change against last week in the top three lines and push everything else down.

Set up this way, a person is left with one job. Open the ERROR list on Monday morning and drive it to zero that week. The "20 minutes of weekly review" from Chapter 1 becomes a real 20 minutes here. Not 20 minutes of eyeballing 200 notes, but 20 minutes of fixing three lines somebody already found. Automating the check does not mean people step back. It means the 20 minutes a person spends moves from finding to fixing.

Count only what actually improves when the number goes up

Once the check runs you have numbers, and once you have numbers you want to report them. Here is where the most common mistake shows up. People count notes.

Note count is easy to raise. Create thirty empty notes and it goes up. A vault grown that way is worse than before. Same reason Chapter 15 said not to count records per person. A metric that is easy to game will be gamed. Not out of bad faith. People move toward whatever you measure.

Ask three questions of every metric before you pick it.

Three questions for a metric

  • Can a script count it? A metric a person counts by hand disappears within two months. No exceptions.
  • Does raising it require real work? A number you can raise with a few clicks will be raised exactly that way.
  • Do you know what to do when it gets worse? Do not measure a metric with no answer. It leaves anxiety behind and changes nothing.
MetricHow you count itWhy it cannot be gamed
Share of grounded notes Notes with at least one wikilink in the body or a filled evidence field ÷ total To make a link you need a real note to point at. Pour in empty notes and the denominator grows, so it goes down instead
Share of reviewed notes confidence: reviewed ÷ total It only rises when a person reads something
ERROR count trend The first line of the weekly check Lowering it means fixing notes or changing rules, and the rules live in the design doc and take a meeting to change
Broken link count The number of wikilinks with no target note Deleting links lowers it too, but that drags the grounded share down with it
Share of "no record" answers The share of AI answers where it found no evidence It only falls when the vault genuinely fills up

Look closely at the first metric. It is the share of grounded notes, not the number of notes. A growing denominator drops the ratio, so pouring in empty notes makes the metric worse. That is the shape of a good metric. The shortcut is blocked and only the honest road is open.

Adding it to the script takes a few lines. Put them after the check body and before the saving code, because the saving code uses the total and reviewed built here.

# Record metrics as ratios, not counts

def gr_body(text):                    # the body with the frontmatter removed
    m = FM.match(text)
    return text[m.end():] if m else text

total = len(notes)
if not total:                                  # avoid dividing by zero on an empty first-day vault
    add("INFO", "_", "No notes yet. Metrics start once notes exist")
    total = 1
grounded = 0
for p in notes.values():
    t = p.read_text(encoding="utf-8")
    # exactly as defined: a wikilink in the body or a filled evidence field
    if LINK.search(gr_body(t)) or (frontmatter(t) or {}).get("evidence"):
        grounded += 1
reviewed = sum(1 for m in metas if m.get("confidence") == "reviewed")

add("INFO", "_", f"grounded notes {grounded}/{total}"
                 f" ({grounded * 100 // total}%)")
add("INFO", "_", f"reviewed notes {reviewed}/{total}"
                 f" ({reviewed * 100 // total}%)")

There is a reason gr_body has to exist. Sweep the frontmatter as well and a note with nothing but owner: "[[Kim]]" counts as grounded. That is an owner field, not evidence. When the definition of a metric and the code that counts it drift apart, the metric measures nothing.

The ratios you calculate attach as two lines in the INFO section after the report's summary line. Since order runs ERROR, WARN, INFO, the INFO section sits at the bottom of the list. Reading only those two lines each week tells a person which way the vault is heading.

One last word about when to start. Do not switch on five metrics at once. Start with one. For the first month, "share of reviewed notes" on its own is enough. Watch it move up and down, get a feel for what moves it, and then add one more.

With five metrics, five numbers move every week, and then you cannot tell which action moved which number. Adding metrics is far more likely to add noise than information.

Do measure once today, though. Six months from now somebody asks "has it got better?", and with no first number to compare against you have nothing to say. Chapter 19 makes the same request. Measurement has to start when you start.

Solbit Tech in practice: what 19 ERRORs on the first run revealed

Back to that first run. It produced 19 ERRORs and Kim got ready to fix 19 notes. But grouping the list by cause showed that most of them had one cause.

They were notes with no updated field, and every one had been written by hand before the Chapter 12 templates existed. So people had not broken a rule. The notes predated the rule.

What got fixed, then, was not the notes. They added one line to CLAUDE.md, "every new note starts from a template", and filled updated on twelve old notes from the file modification time. It took 20 minutes.

Since then ERRORs hover around three. They never reached zero. Make a new note and some fields sit empty for a few days. The target is not zero, it is "not going up". If notes grow and ERRORs do not, quality is holding.

One more thing surprised them. Most of the broken links were traces of a rename. Rename inside Obsidian and the links follow. Rename in File Explorer and they do not. Without the check they would never have found that habit.

Try it: run your first check

Do not aim for a perfect script. The goal is to run it once.

  1. Join the code above in the order configuration, body, metrics, saving, save it as _ops/scripts/validate.py, and swap REQUIRED, STATUS_ENUM and FORBIDDEN for your own company's lists. The ones you fixed in Chapter 9.
  2. Run it once. Step 3 of the "before that" section above, or hand it to Cowork for the same result. More than twenty ERRORs is normal. Do not be alarmed.
  3. Group the list by cause. Two or three causes usually account for most of it.
  4. Pick the biggest cause and fix whatever created it, not the notes. It will be a template or one line of CLAUDE.md.
  5. Add one new check as a WARN. Two weeks later, promote it to ERROR if there were no false positives at all, and delete it if there was even one.
  6. Schedule it for Friday using the Chapter 14 method. Do that and this chapter is done.

Quick recap

  • Rule violations pile up quietly, because they are invisible, because there is no reason to report them, and because somebody else pays later
  • "Manage it well" is not a management method. Nobody eyeballs 200 notes a week past the second week
  • Five checks are enough to start with: missing required field · vocabulary violation · broken link · stale note · forbidden name
  • The heart of this chapter is not the script but the level design. Only put things in ERROR that have to be zero
  • Make everything an ERROR and week one gives you 200, and by week three nobody looks. A number you cannot act on is noise
  • A new check starts in WARN and gets promoted after two weeks of watching. Demotion rarely works
  • One false positive kills trust in the whole list. People trust a list list by list, not item by item
  • Never put something whose answer varies by person into code. That is your false positive
  • Write vault-relative paths in the report, not filenames. Merge same-named files and your counts go quietly wrong
  • Run it weekly. Results pile up in _reports/ and one trend line flows into the dashboard in _moc/
  • Pick metrics with the shortcut blocked, like the share of grounded notes rather than the number of notes
