# Solbit Tech Wiki · rules for AI

Last edited: 2026-07-30 · Maintained by: Kim
Only people edit this file. AI may suggest.

## 0. What this vault is

- The vault holding Solbit Tech's company knowledge.
- Company facts live only in notes under Sources/. Do not source facts elsewhere.
- Definitions of classes, relations, fields and vocabulary are in
  _ops/01-ontology-design.md. When judgment is split, follow that document.
- When rules conflict, the lower number wins.

## 1. Absolute rules (no exceptions)

1. Never fill in a fact that is missing. If it is not in the vault, answer "no record".
2. Never write a number with no evidence. Write 확인 필요 instead.
3. Name the evidence note alongside the answer. Drop any sentence you cannot back.
4. On finding something that contradicts an existing note, do not fix it.
   Report it separately as a contradiction.
5. Never guess a person's name or title. Use the wording from the source.
6. Never cite a note with confidence: draft in an external document.

## 2. Fields and vocabulary

- A closing date is always due. Never invent another name.
- Relations are pdm_uses / pdm_output_of / pdm_intent_of. The owner is written as owner.
- Relation values are links in the form "[[note name]]". For several, break lines.
- status: for 제품, 기획 / 개발 / 운영 / 중단. For 과제 and 기회,
  기획 / 진행 / 검토 / 완료 / 보류.
- confidence: draft or reviewed. Never invent another value.
- Never create a field that is not in the design document. Suggest it to a person instead.

## 3. Rules for writing files

- You may create files on your own in two places, _reports/ and _moc/.
- Notes under Sources/ are shown as a table first and created or edited only after approval.
- Files under _ops/ and this file are edited by people only.
- New notes carry confidence: draft and updated set to today's date (KST).
- Put this sentence at the top of any generated file:
  "This file is generated. Edit it by hand and your edit disappears on the next run."

## 4. Confidentiality

- confidential values: 공개 / 사내 / 대외비. No value means 사내.
- Never write the company name from a 대외비 note into an external document.
  Mask a pre-contract customer as "a domestic logistics company".
- Personal data, accounts and passwords, payroll and HR material do not belong in the vault.
  On finding any, stop work and tell a person.

## 5. Facts about us that are easy to get wrong

These caused accidents because documents disagree. The side written here is right.

- WareTwin's TRL is 4. The 6 in old material was corrected as overstated.
  Evidence: DEC-2026-0715-TRLCorrection.
- Daesung Logistics is pre-contract. Never use it as a delivery or a reference.
- Pickview has no pilot data. Never cite it as proposal evidence.
- Warebot went into service in April 2023. Do not round it to "launched in 2023".
- "Lee CEO" and "Kim CEO" stay separate spellings until confirmed. Do not merge them.
- CAP-ObjectRecognition is an output of PRJ-2025-SmartLogistics. Never call it in-house.

## 6. When answering

- If the vault has no answer, say "no record" first,
  then say which note the fact should be written into.
- If a table will do, answer with a table. Do not pad it out.
- For work that needs approval, show it first and wait. Never run ahead.

Do not leave section 5 empty

Sections 0 through 4 are nearly the same at any company. Only section 5, "facts about us that are easy to get wrong", is yours. Every time the AI makes the same mistake twice, add a line. The longer this section grows, the better the answers get.

Validation script

When you use it · every morning, or every Friday

Save it as _ops/scripts/validate.py and run it automatically. It catches five things: missing required fields, status values outside the controlled vocabulary, forbidden field names, broken links and stale notes. No external libraries, so there is nothing to install.

Where it came from. Chapter 17. How to put it on a schedule is in Chapter 14.

Join the four pieces below and you have one file. Configuration and parser, the check loop, the metrics, the report output, in that order. The metrics have to come before the report. The last piece uses values the metrics build.

# _ops/scripts/validate.py
# Check the vault rules in code. No external libraries.

import re, sys, datetime
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]   # top of the vault
TODAY = datetime.date.today()
STALE_DAYS = 30

# Required fields per class. If this table and the layer 1 design doc
# disagree, the design doc wins.
# class, id and updated are required everywhere. The rest varies by class.
REQUIRED = {
    # the four backbone classes from Chapter 9
    "제품":     ["class", "id", "updated", "status", "owner", "since"],
    "기술역량": ["class", "id", "updated", "trl", "evidence"],
    "과제":     ["class", "id", "updated", "period", "funder", "budget"],
    "기회":     ["class", "id", "updated", "stage", "due"],
    # the three support classes from Chapter 9
    "조직":     ["class", "id", "updated"],
    "사람":     ["class", "id", "updated"],
    "결정":     ["class", "id", "updated", "date"],
    # Not classes. These are note kinds inside 40-Worklog. See Chapter 12.
    # Leave them out and you get a flood of "class value not in the
    # design doc list" ERRORs, so they are listed here too.
    "회의록":   ["class", "id", "updated", "date"],
    "업무로그": ["class", "id", "updated", "owner"],
}

# The status vocabulary differs by class. One global set gives you
# a flood of false positives.
STATUS_ENUM = {
    "제품": {"기획", "개발", "운영", "중단"},
    "과제": {"기획", "진행", "검토", "완료", "보류"},
    "기회": {"기획", "진행", "검토", "완료", "보류"},
}

# Forbidden names. One meaning under all different names cannot be
# counted. Every name on the left is a bad example.
FORBIDDEN = {"deadline": "due", "due_date": "due",
             "uses_tech": "pdm_uses", "tech_used": "pdm_uses",
             "used_tech": "pdm_uses"}

findings = []
metas = []                                   # the metrics below use this list
def add(level, where, msg):
    findings.append((level, where, msg))

FM = re.compile(r"\A---\n(.*?)\n---", re.S)

def frontmatter(text):
    m = FM.match(text)
    if not m:
        return None
    meta, key = {}, None
    for line in m.group(1).splitlines():
        if line.lstrip().startswith("-") and key:      # a list item
            meta.setdefault(key, []).append(line.strip(" -").strip('"'))
            continue
        m2 = re.match(r"([A-Za-z_가-힣]+):\s*(.*)$", line)
        if m2:
            key = m2.group(1)
            val = m2.group(2).strip().strip('"')
            meta[key] = val if val else []
    return meta
notes = {p.stem: p for p in (ROOT / "Sources").rglob("*.md")}
LINK = re.compile(r"\[\[([^\]|#]+)")

for stem, path in sorted(notes.items()):
    where = path.relative_to(ROOT).as_posix()   # vault-relative path, not filename
    text = path.read_text(encoding="utf-8")
    meta = frontmatter(text)

    if meta is None:
        add("ERROR", where, "no frontmatter")
        continue

    metas.append(meta)                             # collected here for the metrics

    cls = meta.get("class")
    if cls not in REQUIRED:
        add("ERROR", where, f"class value not in the design doc list: {cls!r}")
        continue

    for field in REQUIRED[cls]:                       # 1. required fields
        if not meta.get(field):
            add("ERROR", where, f"missing required field: {field}")

    st = meta.get("status")                            # 2. controlled vocabulary
    if st and st not in STATUS_ENUM.get(cls, set()):
        add("ERROR", where, f"status outside the {cls} vocabulary: {st!r}")

    for bad, good in FORBIDDEN.items():                # 3. forbidden names
        if bad in meta:
            add("ERROR", where, f"forbidden name {bad}. use {good} instead")

    for target in set(LINK.findall(text)):             # 4. broken links
        if target.strip() not in notes:
            add("ERROR", where, f"broken link: [[{target.strip()}]]")

    upd = meta.get("updated", "")                      # 5. stale notes
    if not re.fullmatch(r"\d{4}-\d{2}-\d{2}", str(upd)):
        add("ERROR", where, "updated is not in YYYY-MM-DD form")
    elif st in ("진행", "운영"):
        age = (TODAY - datetime.date.fromisoformat(upd)).days
        if age > STALE_DAYS:
            add("WARN", where, f"unchanged for {age} days (status: {st})")

    if meta.get("confidence") == "draft":
        add("INFO", where, "waiting for human review")

Chapter 17 says to record metrics as ratios rather than counts, because counts rise on their own as the notes grow.

# Record metrics as ratios, not counts

def gr_body(text):                    # the body with the frontmatter removed
    m = FM.match(text)
    return text[m.end():] if m else text

total = len(notes)
if not total:                                  # avoid dividing by zero on an empty first-day vault
    add("INFO", "_", "No notes yet. Metrics start once notes exist")
    total = 1
grounded = 0
for p in notes.values():
    t = p.read_text(encoding="utf-8")
    # exactly as defined: a wikilink in the body or a filled evidence field
    if LINK.search(gr_body(t)) or (frontmatter(t) or {}).get("evidence"):
        grounded += 1
reviewed = sum(1 for m in metas if m.get("confidence") == "reviewed")

add("INFO", "_", f"grounded notes {grounded}/{total}"
                 f" ({grounded * 100 // total}%)")
add("INFO", "_", f"reviewed notes {reviewed}/{total}"
                 f" ({reviewed * 100 // total}%)")
order = {"ERROR": 0, "WARN": 1, "INFO": 2}
findings.sort(key=lambda f: (order[f[0]], f[1]))
n = {lv: sum(1 for l, _, _ in findings if l == lv) for lv in order}

lines = [f"# Vault check {TODAY}", "",
         f"- ERROR {n['ERROR']} · WARN {n['WARN']} · INFO {n['INFO']}",
         f"- notes checked: {len(notes)}", ""]
for lv in ("ERROR", "WARN", "INFO"):
    group = [(w, m) for l, w, m in findings if l == lv]
    if not group:
        continue
    lines.append(f"## {lv} {len(group)}")
    lines += [f"- `{w}` {m}" for w, m in group]
    lines.append("")

(ROOT / "_reports").mkdir(exist_ok=True)
(ROOT / "_reports" / f"check-{TODAY}.md").write_text(
    "\n".join(lines), encoding="utf-8")

# Raw material for the Chapter 15 trend chart. One line per run.
# Columns: date, ERROR, WARN, INFO, total notes, reviewed share (%)
# The last column is the line Chapter 15 draws. Without it, no chart.
with (ROOT / "_reports" / "validate-history.csv").open(
        "a", encoding="utf-8") as f:
    f.write(f"{TODAY},{n['ERROR']},{n['WARN']},{n['INFO']},"
            f"{len(notes)},{reviewed * 100 // total}\n")

sys.exit(1 if n["ERROR"] else 0)

# Structuring source material

## When to use
- After a meeting, putting the memo into the vault
- Putting a document or a public call received from outside into the vault

## Input
- One piece of source text, or one file path
- Without it, do not start. Ask for the source

## Procedure
1. Save the source first.
   Meeting memos go in Sources/40-Worklog/, material received from outside and
   transcripts go in Sources/90-Reference/.
   Name the file YYYY-MM-DD-title.
2. Pull four things out of the source.
   - Decisions: anything of the form "we decided to". With the alternatives and the reasoning
   - Actions: anything with an owner and a date
   - Fact changes: anything that changes a field on an existing note
   - New entities: organizations, products or technologies with no note yet
3. Report what you pulled out as a table. Do not create files yet.
4. Create or edit notes only after approval.
5. Use the matching template from _ops/templates/ for any note you create.
6. Finally, add links to the "Extracted from this" section of the source note.

## Rules
- New notes are created with confidence: draft
- Every extract links back to the source with source:
- Never fix content that contradicts an existing note. Report it separately as a contradiction
- Mark pre-contract customers as confidential: 대외비
- Never smooth over something ambiguous. Leave it as 확인 필요

## Output
- 1 source note (never modified)
- 0 or more extracted notes
- A report table (in the chat window)

## Do not
- Never edit the source. Leave the typos and the broken sentences
- Never infer a fact that is not in the source
- Use people's names exactly as written in the source. Never guess a title and attach it
- Never set confidence to reviewed. Only people change that
- Never create or edit files under Sources/ without approval

# Intent against execution retrospective

## When to use
- The quarterly retrospective in the last week of the quarter
- Revising the quarterly plan mid-way

## Input
- A period (start date and end date). Without one, use the previous quarter

## Procedure
1. Gather the work logs for that period from Sources/40-Worklog/.
2. Follow each log's pdm_intent_of link and open the target project or opportunity note.
3. Group by project and lay each one out in three lines.
   - Plan: that project note's stage and due
   - Actual: what the logs actually record
   - Gap: where the two diverge
4. Collect logs with no pdm_intent_of separately as "work not connected to anything".
5. Mark days with no log as "no record". Never fill them in by guessing.

## Rules
- Write around "progress and blockers", not "what I did"
- On finding a gap, do not assert a cause. Record the gap only
- Never write a sentence that evaluates a person. Names and facts only
- Under 1500 characters

## Output
- _reports/retro-YYYY-QQ.md
- On the first line, the change in "work not connected to anything" against last time

## Do not
- Never edit notes under Sources/
- If the logs are empty, do not produce a retrospective. Leave one line saying "no record"
- Never add unplanned work into the plan after the fact

# Vault convention check

## When to use
- The first Monday of every month
- Right after editing the ontology design document

## Input
- _ops/01-ontology-design.md and _ops/02-terminology.md
- Without them, do not start

## Procedure
1. Read the latest results from _ops/scripts/validate.py first.
   Do not look again at anything it already caught.
2. Look only at the four things the script cannot catch.
   - a number written down with no link to an evidence note
   - confidence: reviewed with an empty evidence section
   - frontmatter values that disagree with the body text
   - different values recorded for the same entity
3. Report only what is certain. If it is borderline, do not report it.
4. Maximum 3 items. Beyond that, keep the 3 most serious.
5. For each item, name the file and the line number.

## Rules
- Fix nothing. Produce a list only
- Compare with the previous report and put the change on the first line
- If there are no violations at all, write one line: "no violations"

## Output
- _reports/audit-YYYY-MM-DD.md

## Do not
- Never edit or create files under Sources/
- Never repeat an item the script has already reported
- Never write "suggested improvements". Facts only

Do not schedule all ten

Technically you can build as many as you like. What an organization tolerates tops out at three a week. Past that people mute the channel, and once they mute it they miss the announcements that matter. Every time you create a new job, review an existing one as a deletion candidate.

Leave these three lines on notes the AI creates. They stop unverified material leaking into external documents.

confidence: draft      # AI made it, nobody has looked
confidence: reviewed   # a person read it and confirmed it
generated_by: schedule/weekly-briefing   # which automation made it

Dashboard and visuals

When you use it · when somebody says they cannot see what recording buys them

Scheduled task 4 rebuilds the dashboard note every week. For people who do not use Obsidian, send the single HTML page the script produces. Maintain it by hand and within three weeks you have a wrong diagram.

Where it came from. Chapter 15. The layout rules and what you must not measure are there.

Dashboard generation script

# _ops/scripts/dashboard.py — the core part only
# read the frontmatter and render one HTML file. No external libraries.

import re, datetime
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]
rows = []
for md in (ROOT / "Sources" / "20-Projects").glob("*.md"):
    text = md.read_text(encoding="utf-8")
    fm = re.match(r"---\n(.*?)\n---", text, re.S)
    if not fm:
        continue
    meta = dict(
        re.findall(r"^(\w+):\s*\"?([^\"\n]+)\"?$", fm.group(1), re.M)
    )
    rows.append((md.stem, meta.get("status", "unset"),
                  meta.get("due", ""), meta.get("owner", "")))

rows.sort(key=lambda r: r[2] or "9999")
today = datetime.date.today().isoformat()

html = [f"<h1>Project status <small>{today}</small></h1><table>"]
for name, status, due, owner in rows:
    d_day = ""
    if due:
        left = (datetime.date.fromisoformat(due) - datetime.date.today()).days
        d_day = f"D{left:+d}"
    cls = "urgent" if d_day and left < 21 else ""
    html.append(f"<tr class='{cls}'><td>{name}</td><td>{status}</td>"
                f"<td>{due} {d_day}</td><td>{owner}</td></tr>")
html.append("</table>")

(ROOT / "_reports" / "dashboard.html").write_text(
    "<style>.urgent{background:#FAEADF}</style>" + "\n".join(html),
    encoding="utf-8")

The six lines that get added when it becomes a scheduled task

In a conversation you fix a bad result on the spot. On a schedule there is nobody there to do that. That is why Chapter 14 insists on these six.

  • The exact location of the output. Without it the result stays in the chat window and vanishes
  • What to do when the result is empty. Without it, "nothing in particular" piles up verbosely every week
  • A never-do-this list. Without it, it quietly edits a note a person has verified
  • A duty to mark evidence. Without it you cannot tell where a number came from and end up checking again
  • A comparison against the previous round. Without it you do not know whether things are improving
  • A length limit. Without it, nobody reads it three weeks later

The order to take things in

  • Day one. CLAUDE.md and the note templates. Nothing else has anywhere to go yet
  • Week two. The wiki-ingest skill and the Chapter 7 connection prompts. Knowledge has to start coming in before the rest means anything
  • Week four. The validation script and scheduled task 1. Add one at a time and watch for two weeks
  • Month two. The dashboard and scheduled task 4. This is where the benefit starts being visible
  • Month three. wiki-audit and wiki-retro and the rest of the scheduled tasks. Before the data piles up they run and return nothing
