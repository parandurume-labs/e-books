# 집필 지침 — 회사용 LLM Wiki 만들기

> 이 파일은 미작성 장을 쓰는 사람이 `STYLE.md`, `OUTLINE.md`, `tools/invariants.json` 과
> **함께** 읽는다. 여기 적힌 사실은 이미 출간된 장에서 확정된 것이라 바꿀 수 없다.

## 1. 산출물 형식

`tools/frag/chNN.frag.html` 파일 하나. 맨 위에 META 주석, 그 아래 `<article>` 하나.
전체 HTML 문서를 쓰지 않는다. 머리말·사이드바·꼬리말은 빌더가 붙인다.

```
<!--META {
  "file": "ch05.html",
  "num": "5",
  "title": "옵시디언과 볼트 이해하기",
  "subtitle": "한 줄짜리 부제",
  "desc": "검색 결과에 뜨는 두 문장. 이 장에서 무엇을 얻는지 적는다",
  "minutes": "12",
  "prev_href": "ch04.html",
  "prev_label": "이전: 도구 세 개의 역할 분담",
  "next_href": "ch06.html",
  "next_label": "다음: Teams 공유폴더로 팀 전체에 연결하기"
} -->
  <article>
    ...
  </article>
```

`minutes` 는 본문 글자 수 ÷ 700 으로 계산한다(한국어 분당 700자 기준).

## 2. 분량

본문(태그 제외) **8,000~13,000자**. 이미 나온 장이 6,300~14,300자다.
짧으면 얄팍하고 길면 안 읽힌다. `<h2>` 는 5~8개.

## 3. 절대 바꿀 수 없는 사실 (출간된 장에서 확정)

### 4층 모델 — 이 책의 뼈대

| 층 | 이름 | 무엇인가 | 파일로는 |
|---|---|---|---|
| 0층 | 분류 | 폴더 계층. 「이 노트를 어디 넣나」 | `Sources/10-Products/` |
| 1층 | 온톨로지 | 클래스·관계·필드·제약의 **정의**. 회사 사실은 한 건도 없다 | `_ops/01-온톨로지-설계서.md` |
| 2층 | 지식 그래프 | 1층을 실제 사실로 채운 것. 답이 나오는 곳 | `Sources/**/*.md` |
| 3층 | LLM Wiki | 0~2층 + AI 규칙 + 스킬·스케줄 + 운영 습관 | 볼트 폴더 전체 |

**「온톨로지가 답을 준다」는 틀린 문장이다.** 답은 2층이 준다.
이 개념을 처음 쓰는 장에서는 3장을 참조로 걸어준다.

### 폴더 구조

```
Sources/
├── 00-Company/     회사·조직·역량·IP
├── 10-Products/    제품
├── 20-Projects/    과제
├── 30-Partners/    고객·파트너
├── 40-Worklog/     업무로그·결정
└── 90-Reference/   참고자료
_ops/               온톨로지 설계서, 표준 어휘, 스크립트
_reports/           자동 생성물
_moc/               지도 노트
```

### 클래스와 ID 접두어

| 클래스 | 접두어 | 판정 기준 | 필수 필드 |
|---|---|---|---|
| 제품 | `PRD-` | 외부에 판매·납품하는 단위 | status, owner, since |
| 기술역량 | `CAP-` | 재사용 가능한 기술 묶음 | trl, evidence |
| 과제 | `PRJ-` | 계약 또는 예산이 붙어 있는 것 | period, funder, budget |
| 기회 | `OPP-` | 계약·예산이 아직 없는 것 | stage, due |

### 정본 필드명 — 다른 이름을 쓰면 안 된다

- 관계: `pdm_uses`, `pdm_output_of`, `pdm_owner`, `pdm_intent_of`
- 상태: `status`, `stage`, `priority`, `blocked_by`, `confidence`
- 메타: `class`, `id`, `owner`, `start`, `due`, `updated`, `since`, `confidential`
- 과제: `period`, `funder`, `budget`

**금지어**: `deadline`, `마감일`, `uses_tech`, `tech_used`, `사용기술`.
마감 날짜는 언제나 `due` 다. 「나쁜 예」로 인용할 때만 쓸 수 있고,
그때는 바로 옆에 나쁜 예라는 표시가 있어야 한다.

### 상태 값 — 이 목록 밖의 값을 쓰지 않는다

- 제품 `status`: 기획 / 개발 / 운영 / 중단
- 과제·기회 `status`: 기획 / 진행 / 검토 / 완료 / 보류
- `confidence`: `reviewed` (사람이 확인) / `draft` (AI 초벌)

### 자동화 쓰기 정책

자동화가 파일을 만들어도 되는 곳은 **`_reports/` 와 `_moc/` 둘뿐**이다.
`Sources/` 아래는 사람이 검토한 뒤에만 들어간다.
「`_reports/` 에만 쓴다」처럼 **한 곳만 적는 배타적 표현을 쓰지 않는다.** 두 곳이다.

## 4. 문체 — `STYLE.md` 가 정본이고 여기서는 요점만

- 종결체는 **`~입니다` / `~습니다`**. 이 책의 목소리다. 다른 책과 다르다
- **em dash(—) 절대 금지.** 쉼표, 마침표, 괄호, 줄바꿈으로 푼다
- **「여러분」 금지.** 「~하시면 됩니다」 또는 주어 생략
- `것입니다` 는 1만자당 2회까지. `그 다음` 3회, `수 있습니다` 6회
- 「왜」를 먼저, 「어떻게」를 나중에
- 실패와 함정을 숨기지 않는다
- 기술 용어는 첫 등장에서 풀어 쓴다. 이미 부록 A 용어 사전이 있으니
  `<a href="appendix-a.html#ontology" class="term-link">온톨로지</a>` 처럼 걸어도 된다
- 외부 도구 사양을 적을 때는 **확인 시점(2026년 7월)을 함께 적는다**
- 근거 없는 수치를 지어내지 않는다. 모르면 「확인 필요」라고 쓰거나 아예 안 쓴다

## 5. 컴포넌트 (기존 장에서 실제로 쓰는 것만)

| 클래스 | 용도 |
|---|---|
| `.callout` + `.callout-title` | 핵심 메시지. `.callout-tip` `.callout-warning` 변형 |
| `.case-box` | 솔빛테크 사례 |
| `.pitfall` | 실제로 걸리는 함정 |
| `.steps` | 순서대로 따라하는 절차 |
| `.checklist` | 장 마무리 확인 항목 |
| `.file-tree` | 폴더 구조. 안에서 `<span class="comment">` 사용 |
| `.exercise-box` | 직접 해보기 |
| `.recap-box` | 「잠깐, 정리!」 `<aside>` 로 감싼다 |
| `.next-teaser` | 다음 장 예고 |
| `.prompt-example` + `.bad` / `.good` | 나쁜 예 / 좋은 예 대비 |
| `<pre><code>` | 복붙용 코드·프롬프트·YAML |
| `<table>` | 인라인 스타일 없이 맨 `<table>` 로. CSS 가 알아서 한다 |

**인라인 `style=` 속성을 쓰지 않는다.** 다크 모드에서 깨진다.

### SVG 다이어그램

넣으려면 `<figure class="illustration">` 안에 인라인 SVG.
**맨 앞에 전면 배경 `<rect>` 가 반드시 있어야 한다.** 없으면 다크 모드에서 글자가 안 보인다.

```html
<figure class="illustration">
  <svg viewBox="0 0 720 400" xmlns="http://www.w3.org/2000/svg">
    <rect width="720" height="400" fill="#FFFDF9"/>
    ...
  </svg>
</figure>
```

색: 배경 `#FFFDF9`, 글자 `#3D2B1F`, 보조 글자 `#6B5647`,
강조선 `#C2703C`, 강조 배경 `#FAEBE2`, 청록 강조 `#0F766E` / `#EAF6F4`.

## 6. 장 구성 관례

1. 문제 상황으로 연다. 솔빛테크에서 실제로 벌어진 일
2. 왜 그런 일이 생기는지 설명
3. 어떻게 하는지. 절차·표·코드
4. 함정 (`.pitfall`)
5. 직접 해보기 (`.exercise-box`)
6. 「잠깐, 정리!」 (`.recap-box`)
7. 다음 장 예고 (`.next-teaser`)

## 7. 하면 안 되는 것

- 다른 장의 내용을 다시 설명하지 않는다. 「3장에서 봤듯이」로 넘긴다
- 없는 기능을 지어내지 않는다. 확실하지 않으면 「확인 필요」로 적고 넘어간다
- 표를 인라인 스타일로 꾸미지 않는다
- 이모지를 쓰지 않는다
- 챕터 번호를 임의로 바꾸지 않는다
