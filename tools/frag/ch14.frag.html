승인 대기로 조용히 멈추는 함정

「확인 필요」로 걸어둔 예약 작업이 새벽 3시에 실행되면, 승인 요청 상태로 멈춰 있습니다. 아침에 확인하기 전까지 아무 일도 안 일어납니다. 다음 회차가 오면 지난 회차가 아직 멈춰 있다는 걸 잊습니다.

해결은 둘 중 하나입니다. 승인이 필요한 작업은 사람이 화면 앞에 있는 시간에 걸거나(금요일 17시처럼), 아니면 쓰기 대상을 _reports/로 제한해서 자동으로 돌립니다. 이 책은 후자를 권합니다.

경로 C: 파이썬 + Windows 작업 스케줄러

AI가 필요 없는 일도 많습니다. 「필수 필드가 있는지」, 「링크가 깨졌는지」, 「노트가 몇 개인지」는 판단이 아니라 계산입니다. 이런 건 스크립트가 더 낫습니다. 결과가 항상 같고, 비용이 0원이고, AI 사용량을 안 씁니다.

17장에서 만드는 validate.py를 매일 아침 자동으로 돌리는 방법입니다. 관리자 권한 명령 프롬프트에서 한 줄입니다. 그 창은 시작 메뉴에서 「명령 프롬프트」를 찾아 오른쪽 클릭 → 「관리자 권한으로 실행」으로 엽니다.

schtasks /create /tn "위키 점검" /tr "python \"C:\Users\hong\OneDrive - 솔빛테크\솔빛테크 위키\_ops\scripts\validate.py\"" /sc daily /st 08:00 /f

옵션이 낯설 텐데 네 개만 알면 됩니다.

옵션뜻
/tn작업 이름. 나중에 지울 때 쓴다 (schtasks /delete /tn "위키 점검")
/tr실행할 명령. 경로에 공백이 있으면 안쪽 따옴표를 \"로 이스케이프
/sc주기. daily / weekly / hourly / onlogon
/st실행 시각 (24시간제)

08:00 대신 onlogon 을 쓰는 게 나을 수도 있습니다

08:00에 걸어두면 그 시각에 PC가 꺼져 있는 날은 그냥 지나갑니다. /sc onlogon으로 하면 로그인할 때마다 돌기 때문에 출근 시간이 불규칙해도 매일 한 번은 실행됩니다.

스크립트 첫 줄에 「오늘 이미 실행했으면 종료」를 넣어두면 여러 번 로그인해도 한 번만 돕니다.

스크립트가 리포트를 남기게 해두면, 사람이 볼 필요도 없습니다. Cowork 예약 작업이 그 리포트를 읽어서 사람 말로 요약하면 됩니다. C가 계산하고 A/B가 해석하는 구조가 가장 안정적입니다.

# _ops/scripts/validate.py 의 마지막 부분
# 결과를 사람이 아니라 다음 자동화가 읽게 남긴다

report = ROOT / "_reports" / f"점검-{today}.md"
report.write_text(rendered, encoding="utf-8")

# 예약 작업이 「증감」을 계산할 수 있게 요약 한 줄을 따로 누적한다
# 열: 날짜, ERROR, WARN, INFO, 전체 노트 수, 검증된 노트 비율(%)
with (ROOT / "_reports" / "validate-history.csv").open("a", encoding="utf-8") as f:
    f.write(f"{today},{n_error},{n_warn},{n_info},{n_notes},{reviewed_pct}\n")

마지막 두 줄이 15장의 추이 그래프 재료가 됩니다. 15장이 그리는 선은 마지막 열입니다. 스크립트 전문과 각 값을 만드는 코드는 17장에 있습니다.

경로 D: Power Automate로 Teams에 올리기

리포트를 만들어도 사람이 그 폴더를 열지 않으면 없는 것과 같습니다. 그래서 결과를 Teams 채널로 밀어 올립니다.

Microsoft 365를 쓰신다면 Power Automate가 이미 있습니다. 흐름은 네 단계입니다.

  1. 트리거를 고릅니다

    Recurrence(되풀이)로 매주 월요일 09:00, 표준 시간대를 Seoul로 지정합니다. 시간대를 안 바꾸면 UTC로 돌아서 9시간 어긋납니다.

  2. 파일을 읽습니다

    SharePoint - 파일 콘텐츠 가져오기로 _reports/ 폴더의 최신 리포트를 가져옵니다. 볼트가 Teams 공유 폴더에 있으므로 SharePoint에서 그대로 보입니다.

  3. 필요한 부분만 뽑습니다

    리포트 첫 10줄만 써도 충분합니다. 전문을 카드에 넣으면 아무도 안 읽습니다. 링크를 함께 붙여 「자세히 보기」로 연결합니다.

  4. Teams에 카드로 올립니다

    채널에 흐름 봇으로 사용자 지정 적응형 카드 게시 동작을 씁니다. 지식 담당 채널을 대상으로 하세요.

카드 본문(Adaptive Card JSON)은 이 정도면 충분합니다.

{
  "type": "AdaptiveCard",
  "version": "1.4",
  "body": [
    { "type": "TextBlock", "text": "주간 위키 점검", "weight": "Bolder", "size": "Medium" },
    { "type": "TextBlock", "text": "@{outputs('요약')}", "wrap": true },
    { "type": "FactSet", "facts": [
      { "title": "ERROR", "value": "@{variables('nError')}건" },
      { "title": "지난주 대비", "value": "@{variables('delta')}" },
      { "title": "전체 노트", "value": "@{variables('nNotes')}개" }
    ]}
  ],
  "actions": [
    { "type": "Action.OpenUrl", "title": "리포트 열기", "url": "@{variables('reportUrl')}" }
  ]
}

알림을 몇 개까지 만들 수 있나

기술적으로는 무한합니다. 조직적으로는 주 3회가 상한입니다. 그 이상이면 사람들이 채널 알림을 끕니다. 알림을 끄면 정말 중요한 공지도 못 봅니다.

새 알림을 하나 만들 때마다 기존 알림 하나를 지울 후보로 검토하세요. 이 규칙 하나가 자동화 프로젝트의 수명을 두 배로 늘립니다.

자동화가 만들어내는 새로운 문제 세 가지

1. 동기화 충돌이 늘어납니다

6장에서 다룬 OneDrive 충돌 문제가 여기서 다시 나옵니다. 예약 작업이 사람과 같은 파일을 동시에 건드리면 충돌본이 생깁니다. 예약 작업은 새벽에도 돌아서, 아침에 와서 보면 이유를 알 수 없는 파일명 1.md가 있습니다.

이 규칙 하나로 대부분 해결됩니다

자동화는 _reports/, _moc/ 처럼 자동 생성 전용 폴더에만 새 파일을 쓴다. Sources/ 는 사람의 영역입니다.

노트를 고쳐야 하는 자동화가 있다면, 고치는 대신 「고칠 목록」을 리포트로 남기고 사람이 승인해서 적용하게 하세요. 손이 한 번 더 가지만, 지식 자산이 조용히 오염되는 것보다 훨씬 낫습니다.

2. AI가 만든 것과 사람이 확인한 것이 섞입니다

예약 작업이 매주 노트를 만들면, 몇 달 뒤에 볼트의 절반이 아무도 읽어보지 않은 AI 생성물이 됩니다. 그런데 다음 AI는 그것을 사실로 읽습니다. 이게 반복되면 품질이 조용히 무너집니다.

그래서 12장의 confidence 필드를 자동화에서 반드시 씁니다.

confidence: draft      # AI가 만들고 아무도 안 봤음
confidence: reviewed   # 사람이 읽고 확인했음
generated_by: schedule/주간-브리핑   # 어느 자동화가 만들었는지

CLAUDE.md에도 한 줄 넣습니다. 「confidence: draft인 노트는 대외 문서의 근거로 쓰지 않는다.」 이 한 줄이 제안서에 검증 안 된 정보가 들어가는 길을 막습니다.

3. 실패가 조용합니다

가장 위험한 문제입니다. 예약 작업이 안 돌아도 아무도 모릅니다. 「알림이 안 왔다」는 사실을 알아차리는 사람은 없습니다. 원래 알림이 없는 주도 있으니까요.

그래서 하나는 반드시 매주 오게 만듭니다. 월요일 브리핑을 「내용이 없으면 특이사항 없음 한 줄」로 설계한 이유가 이것입니다. 한 줄이라도 오면 시스템이 살아 있다는 뜻입니다. 두 주 연속 아무것도 안 오면 뭔가 고장 났다는 신호입니다.

솔빛테크는 3개월 동안 예약 작업 다섯 개를 돌렸습니다. 결과는 이랬습니다.

반대로 「매일 뉴스 요약」은 처음부터 잘못된 자동화였습니다. 볼트를 읽지도, 쓰지도 않는 작업이었으니까요. 만들기 쉬워서 만든 것이고, 그런 건 대개 안 씁니다.

예약 작업은 늘어나기만 합니다. 그래서 분기마다 목록을 열고 작업마다 세 가지를 묻습니다.

자동화 정리 세 질문

  • 지난 4주 결과물 중 사람이 실제로 열어본 것이 있나? 없으면 지웁니다. 「언젠가 필요할 것」은 필요하지 않습니다.
  • 이 작업이 만든 것을 다른 문서에 인용한 적이 있나? 있으면 유지 대상입니다. 실제로 쓰이고 있다는 증거입니다.
  • 이 작업이 목적을 달성해서 필요가 없어졌나? 습관을 만들려던 알림은 습관이 생기면 지웁니다.

직접 해보기: 예약 작업 하나 만들기

세 개를 다 만들지 마세요. 하나만 만들고 2주 돌려보는 편이 훨씬 낫습니다.

  1. 앞의 결정 트리로 만들 작업의 경로를 정하세요. 첫 작업은 B(원격·읽기만)를 권합니다. 실패해도 볼트가 안 망가집니다.
  2. 「① 월요일 아침 브리핑」 프롬프트를 복사해서 우리 회사 폴더 이름과 필드 이름으로 바꾸세요. 그대로 쓰면 안 돕니다.
  3. 주기를 걸기 전에 수동으로 한 번 실행해 보세요. 결과가 이상하면 프롬프트를 고칩니다. 이 왕복을 두세 번 하는 게 정상입니다.
  4. 결과물에서 틀린 사실 하나를 찾아보세요. 찾으면 그건 프롬프트 문제가 아니라 볼트 문제입니다. 어느 노트가 비어 있어서 그렇게 됐는지 확인하세요.
  5. 2주 뒤에 자문하세요. 「이 알림을 실제로 읽었나?」 아니라면 지우고 다른 것을 만듭니다.

잠깐, 정리!

  • 지식 시스템은 「기억해서 해야 하는 일」 때문에 죽는다. 그 일들을 시계에 붙이는 것이 이 장의 목적
  • Cowork 예약 작업은 원격에서 돌지만 로컬 폴더에 닿지 못한다. 로컬 파일이 필요한 작업은 PC가 켜져 있을 때만 실행된다
  • 네 경로를 나눠 쓴다. A 로컬 예약(쓰기) · B 원격 예약(읽기) · C 파이썬+작업 스케줄러(계산) · D Power Automate(알림)
  • 고르는 순서: AI 판단이 필요한가 → 볼트에 써야 하나 → PC를 켜둘 수 있나
  • 예약 프롬프트에는 여섯 개를 반드시 쓴다. 산출 위치, 빈 결과일 때의 행동, 금지 목록, 근거 표기, 이전 회차 비교, 길이 상한
  • 자동화가 죽는 방식은 멈춤이 아니라 소음이다. 변화가 없으면 말하지 않게 만든다
  • 자동화는 _reports/ 와 _moc/ 에만 쓴다. Sources/는 사람의 영역이다
  • AI 생성물에는 confidence: draft와 generated_by를 남긴다. 검증 안 된 것이 대외 문서로 새는 것을 막는다
  • 실패는 조용하다. 하나는 반드시 매주 오게 만들어 생존 신호로 쓴다
  • 목적을 달성한 자동화는 지운다. 폐기는 실패가 아니다
