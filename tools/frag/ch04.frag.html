이제 뭘로 만드는지 이야기할 차례입니다. 세 개를 씁니다.

도구역할한 단어로
Microsoft Teams / OneDrive파일을 팀 전체에 동기화배포
Obsidian사람이 노트를 읽고 쓰고 관계를 본다창
Claude CoworkAI가 파일을 읽고 쓰고 검증한다손

중요한 건 세 도구가 같은 폴더 하나를 공유한다는 점입니다. 별도의 서버도, 데이터베이스도, 연동 설정도 없습니다.

Teams / OneDrive: 배포 담당

이미 쓰고 계실 겁니다. Microsoft 365를 쓰는 회사라면 추가 비용이 없습니다.

여기서 Teams가 하는 일은 딱 하나입니다. Teams 공유 폴더 하나를 만들어 구성원 PC에 자동 동기화하는 것. 누가 노트를 고치면 몇 분 안에 나머지 사람 PC에도 반영됩니다.

이게 왜 좋은가

  • 권한 관리는 이미 회사 계정이 합니다. 구성원마다 계정 하나로 접근을 통제합니다. 별도 계정 만들 필요 없습니다.
  • 백업이 자동입니다. OneDrive 버전 히스토리로 되돌릴 수 있습니다.
  • 퇴사 처리가 쉽습니다. 계정 비활성화하면 접근이 끊깁니다.
  • 추가 비용 0원. 이미 있는 걸 씁니다.

대신 생기는 문제

대신 두 가지 문제가 생깁니다. 6장에서 자세히 다루지만 미리 알려드립니다.

문제 1 · 클라우드 전용 파일

OneDrive는 기본 설정에서 파일을 클라우드에만 두고, 열 때만 내려받습니다. 파일 탐색기에는 보이는데 실제로는 PC에 없는 상태입니다.

사람이 옵시디언으로 열 때는 문제가 없습니다. 옵시디언이 열면서 다운로드하니까요. 그런데 AI는 실제로 디스크에 있는 파일만 읽습니다. 그래서 "파일이 있는데 AI가 못 읽는다"는 상황이 생깁니다.

해결은 폴더 우클릭 → 「이 디바이스에 항상 유지」 한 번. 이게 이 책에서 가장 중요한 클릭 한 번입니다.

문제 2 · 동시 편집 충돌

두 사람이 같은 노트를 동시에 고치면 OneDrive가 파일명 1.md 같은 충돌본을 만듭니다. 구글 독스처럼 실시간 병합이 되지 않습니다.

기술로 막을 수 없습니다. 운영 규칙으로 막습니다. 담당 축을 나누고, 업무로그는 작성자 본인만 수정합니다. 6장에서 분담 방법을 구체적으로 다룹니다.

Teams가 아니어도 됩니다

구글 드라이브, Dropbox, 심지어 깃허브 저장소로도 됩니다. 파일을 여러 PC에 동기화해주기만 하면 됩니다. 다만 각각 특성이 있습니다.

방식장점단점
Teams / OneDrive회사 권한 관리와 통합. 추가 비용 없음클라우드 전용 파일 함정. 충돌 병합 안 됨
Google Drive익숙함데스크톱 동기화 앱이 필수. 충돌 처리 비슷
Dropbox동기화가 가장 안정적유료. 권한 관리를 따로 해야 함
Git (GitHub 등)충돌을 제대로 병합. 변경 이력 완벽비개발자에게 진입 장벽이 큼

Git이 기술로만 보면 가장 좋습니다. 다만 비개발자 구성원이 있으면 실제로는 어렵습니다. 커밋과 푸시를 매번 해야 한다면 하루 3분이 하루 10분이 되고, 그러면 아무도 안 씁니다. 기술적 우월성보다 지속 가능성이 중요합니다.

Obsidian: 창 담당

옵시디언은 마크다운 파일을 위키처럼 보여주는 앱입니다. 무료이고, 데이터를 자기 서버에 가져가지 않습니다.

옵시디언이 하는 일

  • 위키링크. [[창고봇]]이라고 쓰면 그 노트로 가는 링크가 됩니다.
  • 백링크. "이 노트를 가리키는 다른 노트들"을 자동으로 보여줍니다. 이게 은근히 강력합니다.
  • 그래프 뷰. 노트 사이 연결을 그림으로 보여줍니다. 고립된 노트가 한눈에 보입니다.
  • 빠른 검색. 전체 볼트를 즉시 검색합니다.

옵시디언이 안 하는 일

이게 더 중요합니다. 옵시디언은 데이터를 자기 형식으로 가두지 않습니다.

이 조합을 고르는 진짜 이유

우리 지식은 그냥 텍스트 파일로 남습니다. 옵시디언이 없어져도, 회사가 다른 도구로 갈아타도, AI가 바뀌어도 파일은 그대로 열립니다.

노션이나 다른 SaaS 위키는 데이터가 그 회사 서버에 그 회사 형식으로 있습니다. 내보내기가 되긴 하지만 구조가 깨집니다. 회사의 핵심 지식을 남의 형식에 담는 건 위험합니다.

그런데 옵시디언이 꼭 필요한가요

Microsoft 365를 이미 쓰는 회사라면 당연히 나오는 질문입니다. Teams와 OneDrive가 있는데 앱을 하나 더 깔아야 하나 싶습니다.

솔직하게 답하면 이렇습니다. 이 시스템은 옵시디언 없이도 돌아갑니다.

이 책에서 실제로 일하는 것들을 보시면 압니다. Cowork는 폴더의 파일을 직접 읽습니다(7장). 점검 스크립트도 파일을 읽습니다(17장). 대시보드를 그리는 스크립트도 머리말만 봅니다(15장). Power Automate는 SharePoint를 거쳐 읽습니다(14장). 넷 중 어느 것도 옵시디언을 거치지 않습니다. [[창고봇]]이라는 표기도 그냥 글자라서, AI는 옵시디언이 없어도 그 링크를 따라갑니다.

그러면 옵시디언은 무엇을 하나요. 사람이 그래프를 볼 수 있게 합니다. 그게 전부이고, 그게 값을 합니다.

옵시디언을 빼면대신 무엇을 하게 되나
링크를 눌러 옮겨 다니기파일 이름으로 검색합니다. 느리지만 됩니다
백링크(나를 가리키는 노트 목록)스크립트를 짜야 합니다. 자동으로는 안 생깁니다
그래프 뷰없습니다. 5장에서 픽뷰가 외톨이 점으로 드러나는 장면이 이걸로 나옵니다
이름 바꿀 때 링크 따라 바뀌기탐색기나 SharePoint에서 바꾸면 링크가 전부 끊깁니다(부록 C)

마지막 줄이 실무에서 제일 아픕니다. 노트 이름은 생각보다 자주 바뀝니다.

뺄 수 있다는 것이 오히려 근거입니다

이 책은 노션 같은 도구를 권하지 않습니다. 데이터가 남의 형식에 갇히기 때문입니다. 그 잣대를 옵시디언에도 그대로 대면, 빼도 아무것도 잃지 않는다는 사실이 합격 판정입니다. 볼트는 그냥 폴더이고 노트는 그냥 텍스트 파일입니다.

그래서 이렇게 정리하시면 됩니다. 동기화(Teams/OneDrive)와 Cowork는 빼면 시스템이 멈춥니다. 옵시디언은 빼도 돌아갑니다. 다만 무료이고 가둬두는 것이 없으니, 뺄 이유도 딱히 없습니다.

한 가지만 주의하시면 됩니다. OneNote나 Loop처럼 자기 형식으로 저장하는 도구는 옵시디언 자리를 대신할 수 없습니다. 그건 창을 바꾸는 게 아니라 이 책의 전제를 버리는 일입니다.

플러그인은 안 써도 됩니다

옵시디언에는 방대한 커뮤니티 플러그인 생태계가 있습니다. AI 플러그인도 많습니다. 다만 이 책에서는 플러그인을 쓰지 않습니다.

이유가 있습니다. 실제로 이 시스템을 만들 때 LLM 위키 플러그인을 하나 도입했다가 3주 뒤에 걷어냈습니다. 그 판단 과정은 13장에서 자세히 다루지만, 핵심 이유는 이랬습니다.

  • 플러그인이 쓰는 AI 모델이 우리 회사 온톨로지를 이해하지 못했습니다.
  • 한국어 원문에서 뽑은 노트를 영어로 만들어서 회사 고유명사가 번역·왜곡됐습니다.
  • 사람이 검증한 노트와 경쟁하는 저품질 중복 노트가 생길 구조였습니다.
  • 같은 일을 Claude Cowork가 더 잘했습니다.

플러그인이 나쁘다는 게 아닙니다. 같은 일을 하는 도구가 두 개면 둘 다 신뢰할 수 없게 된다는 게 교훈입니다.

Claude Cowork: 손 담당

여기가 이 시스템의 실제 동력입니다.

Claude Cowork는 Claude 데스크톱 앱의 기능으로, 우리 컴퓨터의 폴더를 직접 읽고 씁니다. 채팅창에 파일을 업로드하는 게 아니라, 폴더 자체에 접근합니다.

업로드와 폴더 접근의 차이

파일 업로드 (일반 채팅)폴더 접근 (Cowork)
대상내가 고른 파일 몇 개폴더 전체
전체 검색불가능가능 (정규식 검색까지)
파일 수정불가능 (새 파일을 받아 내가 저장)직접 수정
여러 파일 일괄 작업불가능가능
코드 실행불가능가능 (파이썬 스크립트 등)
매번 다시 올리기필요불필요

세 번째와 다섯 번째 줄이 결정적입니다. AI가 볼트를 대상으로 코드를 써서 돌립니다. 품질 점검, 일괄 수정, 링크 분석이 전부 여기서 나옵니다.

사례 · 솔빛테크의 첫날

솔빛테크가 이 시스템을 처음 세팅한 날, Claude가 한 일은 이랬습니다.

  • 볼트 폴더 전체를 훑어 기존 자료 105개 파일의 구조를 파악
  • 온톨로지 설계서·용어집·운영가이드·템플릿 7종 등 파일 40개 생성
  • 품질 점검용 파이썬 스크립트를 작성해서 실행 → 규칙 위반 19건 발견
  • 19건을 일괄 수정하고 재실행 → 0건 확인

여기서 눈여겨볼 건 세 번째와 네 번째입니다. AI가 자기가 만든 결과물을 스스로 검증했습니다. 실제로 YAML 문법 실수 몇 개가 있었고, 스크립트가 그걸 잡았습니다.

파일 업로드 방식으로는 이게 안 됩니다. 코드를 돌릴 수 없으니까요.

Cowork가 못 하는 것

정직하게 한계도 적겠습니다.

못 하는 것영향
옵시디언 앱 내부 기능 실행플러그인 버튼을 누르거나 그래프 뷰를 볼 수 없습니다. 다만 링크는 텍스트라 직접 분석 가능합니다.
모바일에서 사용데스크톱 앱 전용입니다.
클라우드 전용 파일 읽기앞서 말한 OneDrive 함정. 「항상 유지」 설정이 필요합니다.
규칙 위반을 강제로 차단규칙은 AI가 읽고 지키는 방식입니다. 사후 검증 구조입니다. 그래서 17장의 검증 스크립트가 필요합니다.

많이 받는 질문: "MCP를 만들어야 하나요?"

이 주제를 알아보면 MCP(Model Context Protocol)라는 말이 나옵니다. AI를 외부 도구·서비스에 연결하는 표준 규격입니다. 옵시디언용 MCP 서버도 여러 개 공개되어 있습니다.

이런 질문을 많이 받습니다. "옵시디언 MCP를 깔아야 하나요? 우리 전용으로 만들어야 하나요?"

답: 지금은 필요 없습니다

옵시디언 볼트는 그냥 마크다운 파일 더미입니다. Cowork가 폴더를 직접 다루므로 접근을 위한 MCP는 불필요합니다. 오히려 파일 직접 접근이 더 강력합니다. 전체 검색, 코드 실행, 일괄 편집은 MCP 도구 호출로는 느리거나 아예 안 됩니다.

MCP가 실익이 있는 경우는 따로 있습니다.

상황선택
PC에서 볼트를 읽고 쓰고 싶다Cowork 폴더 접근. MCP 불필요
모바일이나 일반 채팅에서 볼트를 조회하고 싶다커뮤니티 MCP (Local REST API 계열)
규칙 위반을 사후 검증이 아니라 사전에 차단하고 싶다전용 MCP 직접 개발

세 번째가 유일하게 진짜 실익이 있는 경우입니다. MCP 서버는 "잘못된 형식이면 거부"를 예외 없이 실행합니다. AI가 규칙을 잊어도 서버가 막습니다.

이건 먼저 문제를 관찰한 뒤에 만드는 게 맞습니다. 아직 겪지 않은 문제를 위해 시스템을 설계하면, 필요 없는 것을 만들고 필요한 것을 놓치게 됩니다. 2~3주 운영해 보면 "실제로 규칙이 얼마나 깨지는지"를 데이터로 알게 됩니다. 그때 판단하면 됩니다.

이 책의 태도

도구를 적게 씁니다. 하나로 되면 하나만 씁니다.

지식관리 시스템이 죽는 가장 흔한 이유는 도구가 부족해서가 아니라 관리할 게 너무 많아서입니다. 플러그인 5개, MCP 3개, 자동화 스크립트 10개를 깔아두면 6개월 뒤엔 그것들을 관리하는 게 일이 됩니다.

  • 세 도구가 같은 폴더 하나를 공유한다. 서버·DB·연동 설정이 없다
  • Teams/OneDrive = 배포. 권한 관리와 백업을 회사 계정이 이미 해준다. 대신 클라우드 전용 파일 함정과 동시 편집 충돌이 생긴다
  • Obsidian = 창. 위키링크·백링크·그래프. 무엇보다 데이터를 그냥 텍스트 파일로 남긴다
  • Claude Cowork = 손. 폴더 직접 접근. 전체 검색·일괄 수정·코드 실행이 가능하다

  • 도구를 적게 쓴다. 지식관리 시스템은 도구 부족이 아니라 관리 부담으로 죽는다
